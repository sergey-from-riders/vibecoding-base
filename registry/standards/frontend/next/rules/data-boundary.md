# Серверные данные

## Коротко

У чтения/изменения данных должна быть определенная граница ответственности.

## Плохо

```text
Кнопка делает fetch, приводит JSON через «as User» и кеширует по /me.
Два поиска завершаются в обратном порядке; старый ответ заменяет новый.
Сервер возвращает всю запись пользователя и доверяет tenant из браузера.
```

## Хорошо

```text
Сервер: сессия → объектные права → выбор разрешенных полей DTO.
Клиент: декодирование ответа → состояние запроса с ID/ключом.
Новый поиск: отменить прежний; применить ответ только для текущего ID.
Приватный кеш: ключ и invalidation учитывают аккаунт и контракт доступа.
Дополнительный BFF: только при конкретной необходимости преобразования.
```

## Почему

Явные границы предотвращают утечку данных, ошибки несоответствия схемы и появление устаревшего результата без обязательного множества слоев.

## Когда применять

Для удаленных или сохраняемых данных. В Next.js App Router разделение внешнего HTTP API, server-only DAL и компонентного чтения выбирается по системе; это альтернативы, которые нельзя механически складывать в обязательную архитектуру.

### Подробные условия

Браузерный клиент выполняет сериализацию, обработку ответа и отмену; серверный доступ проверяет пользователя, объектные права и данные. BFF нужен, только если существующий API не дает требуемого клиентского контракта. Отдельный сервис и универсальный repository не обязательны.

Внешний payload проверяй во время выполнения на границе; TypeScript assertion не валидирует JSON. Передавай клиенту только нужные разрешенные поля. Ключи кеша и политика хранения должны учитывать пользователя/tenant и права; при смене аккаунта очищай соответствующее клиентское состояние. При конкурирующих чтениях публикуй только результат, относящийся к текущему запросу. Отмена экономит ресурсы, но сама по себе не гарантирует, что старый ответ не попадет в UI.

## Как проверить

- Валидный разрешенный ответ → декодировать → UI получает только нужный DTO.
- Чужой tenant или неверный тип поля → запросить/декодировать → сервер отказывает в доступе либо клиент показывает контролируемую ошибку контракта.
- Запрос B завершился раньше A; затем сменился аккаунт → применить ответы → A не затирает B, приватные данные прежнего аккаунта не показаны.

## Человек

Определяет серверный контракт и необходимость дополнительной границы.

## Агент

Проверяет runtime-декодирование, ключи приватного кеша и гонку ответов, не считает типизацию проверкой прав.
