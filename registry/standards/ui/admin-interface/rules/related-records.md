# Связанные записи

## Коротко

Связь хранит стабильный идентификатор, ограничения целостности и проверяемый доступ к цели.

## Плохо

```text
Заказ хранит только введенное название клиента. API принимает ID объекта другого tenant без проверки.
```

## Хорошо

```text
customer_id=42; customer_name_snapshot="ООО Пример".
Кардинальность и on-delete заданы схемой.
Привязка проверяет tenant и права; исторический snapshot не заменяет связь.
```

## Почему

ID обеспечивает целостность, а текстовый снимок может сохранять исторический смысл документа. Эти данные выполняют разные функции. PostgreSQL показывает механизм ссылочной целостности; выбор исторических снимков, прав и поведения редактора является контрактом проекта.

## Когда применять

Для связей между сущностями. Свободный текст допустим для внешней сущности без локального ID или исторического снимка, если это явно определено моделью.

### Требования

- Определите кардинальность, обязательность, уникальность и политику удаления: restrict, null, cascade либо архивирование. Soft delete и восстановление имеют отдельную семантику.
- При присоединении сервер проверяет существование, tenant, право использовать цель и инварианты. При чтении метаданных связи повторно проверяет доступ к раскрываемым полям.
- Для исторических документов храните нужные снимки названий/реквизитов отдельно от ID и укажите момент фиксации.
- Редактор показывает отсутствующую/недоступную/архивную цель без утечки данных; сохранение не превращает ее автоматически в новую связь.

## Как проверить

- Попробуйте присоединить чужой tenant, удаленную и недоступную цель; проверьте серверный отказ.
- Измените название и удалите цель: исторический документ и текущая связь ведут себя по установленной политике.

## Человек

Определяет смысл и кратность связей.

## Агент

Использует ID и проверяет соседние сценарии перехода и поиска.
