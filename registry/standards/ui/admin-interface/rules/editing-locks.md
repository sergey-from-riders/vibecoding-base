# Конкурентное редактирование

## Коротко

Конкурентное редактирование предотвращает потерю обновлений; optimistic concurrency допустима без обязательной блокировки.

## Плохо

```text
Блокировка хранится в браузере. После ее истечения старый редактор сохраняет поверх нового владельца.
```

## Хорошо

```text
Optimistic: save(base_revision=7) → conflict при текущей 8.
Lease-профиль: acquire → token=32, expires_at по серверу; renew проверяет владельца.
После принятия ресурсом token=33 запись с token=32 отклоняется, локальный ввод остается.
```

## Почему

Lease улучшает координацию, но сам по себе не заменяет проверку ревизии. Выбор pessimistic/optimistic определяется конфликтностью задачи. Hazelcast приведен как первичный пример механизма fencing; его внедрение не обязательно.

## Когда применять

Для совместно редактируемых данных. Блокировка всей записи не обязательна, если CAS и разрешение конфликтов обеспечивают нужную семантику.

### Требования

- Определите область конфликта: запись либо независимые поля. Для field-level merge задайте инварианты между полями; несовместимые изменения не объединяются автоматически.
- Optimistic-профиль атомарно проверяет базовую ревизию. Lease-профиль дополнительно задает acquire, renew, release, expiry по серверным часам и владельца.
- При смене владельца выдавайте возрастающий fencing token. Конечный записывающий ресурс атомарно сравнивает token с максимальным ранее принятым значением и отклоняет меньшие значения. До принятия нового token ресурс может еще принять задержанный запрос прежнего владельца: один fencing token не обнаруживает истечение lease.
- Если запись должна запрещаться сразу после expiry или смены владельца, дополнительно проверяйте актуальный lease/owner согласованно с записью. Опишите, какой ресурс обеспечивает эту атомарность; отдельная предварительная проверка с последующей записью оставляет race condition.
- При конфликте/потере lease сохраните локальный ввод, покажите актуальную базу и доступные merge/reload действия. Принудительный захват ограничивается полномочиями и журналируется.

## Как проверить

- Проверьте две вкладки, паузу клиента дольше lease, задержанный запрос прежнего владельца до и после принятия нового token ресурсом, а также несовпадающие часы клиента. Ожидаемый результат должен соответствовать выбранной гарантии fencing либо атомарной проверки lease/owner.
- Проверьте конфликт связанных полей и сохранность локального ввода после отказа.

## Человек

Определяет права освобождения и область блокировки.

## Агент

Реализует серверную проверку владельца, срока и версии, показывает конфликт.
