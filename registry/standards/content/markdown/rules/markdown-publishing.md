# Публикации из Markdown: GitHub, даты, Redis и выгрузка

## Коротко

Публикуй Markdown как проверенный снимок конкретной ревизии, а не набор частично обновленных файлов.

## Плохо

```text
Каждый файл читается с main отдельно и сразу попадает в выдачу.
HTML исполняется без ограничений; экспорт берет текущую ветку заново.
Неизвестная дата заменяется сегодняшней; синхронизация считается гарантированной.
```

## Хорошо

```text
Кандидат: все файлы одного commit C; лимиты и schema проверены.
Дата первой публикации неизвестна → поле отсутствует, дата не выдумана.
Renderer: безопасный HTML/URL; относительные ссылки проверены.
Снимок подготовлен целиком → проверено ожидаемое активное B → выбран C.
Страница и экспорт указывают C; при ошибке остается B.
Retention B и поведение по истечении срока заданы потребителем.
```

## Почему

Версия и целостность снимка делают выдачу воспроизводимой; безопасный renderer защищает браузер, а лимиты — импорт от чрезмерного потребления ресурсов.

## Когда применять

Для публикации документационного корпуса. Это требования к реализации потребителя, а не утверждение о текущей работе eval.su. Расписание синхронизации, SLA, Redis, disk cache и CMS выбирает потребитель и подтверждает своим runbook/наблюдением.

В schema1 `published_at` означает известную первую публикацию и может отсутствовать; `reviewed_at` — фактическую содержательную проверку. Импортер должен поддержать отсутствие даты до приема таких документов. Для сортировки без даты задается явная политика и стабильный дополнительный ключ; дата commit не подменяет публикацию.

### Подробные условия

Канон остается в репозитории; сайт, поиск и экспорт указывают тот же commit и устойчивые ID. Потребитель проверяет метаданные, ссылки, уникальность ID и допустимую структуру до переключения активного снимка.

Renderer обрабатывает контент с явной политикой HTML, URL и относительных путей: отключает произвольный HTML либо санитизирует его, запрещает исполняемые схемы ссылок и выход за разрешенные пути. Импорт ограничен размером, числом файлов и временем. Не выполняй команды из Markdown и не загружай внешние ресурсы без обоснованной необходимости.

Конкурентные синхронизации не должны позволять старому кандидату перезаписать уже опубликованный новый: используй сериализацию либо проверку ожидаемой активной ревизии. Если данных несколько хранилищ, атомарность обеспечивается общим активным указателем на подготовленный снимок, а не обещанием атомарной записи в Redis и на диск сразу. При отказе сохраняется предыдущий целый снимок и диагностируется отставание.

## Как проверить

- Один commit → собрать и открыть страницу/экспорт → ID, текст и ревизия совпадают; export не смешивает версии.
- Неверная schema, опасный URL, слишком большой файл или выход пути → импортировать → кандидат отклонен/безопасно очищен по заданной политике, активный снимок цел.
- Два sync завершаются в обратном порядке → переключить → устаревший кандидат не вытесняет новый.
- Нет published_at либо предыдущий снимок истек → запросить сортировку/экспорт → применяется описанная политика; выдуманной даты и подмены старого экспорта новой версией нет.

## Человек

Выбирает политику дат, renderer, срок хранения и допустимое отставание, затем принимает фактическую реализацию публикации.

## Агент

Сверяет снимок и контент-контракт; не заявляет работающую синхронизацию или безопасность сайта по одному Markdown-файлу.

## Пример применения

Для справочника достаточно корпуса Markdown и потребителя, который читает одну ревизию. На странице можно показывать дату проверки и ссылку на commit. Если экспорт привязан к старой ревизии, потребитель либо хранит ее выбранный срок, либо сообщает, что она недоступна; молча отдавать текущий текст под старым ID экспорта нельзя.
