# Статус проверок

## Коротко

Отчет о проверке указывает объект/commit или digest, состояние diff, среду, команду/метод, область и результат.

## Плохо

```text
Команда не запущена: «Тесты должны проходить».
Схема Markdown валидна: «Все стандарты реализованы и сайт работает».
```

## Хорошо

```text
Artifact C + текущий patch P, среда test.
Schema: passed; unit scenario AC-2: passed.
Browser E2E: blocked — браузерная среда недоступна.
Фактическая публикация: not-run.
Вывод ограничен этими проверками; runtime-соответствие не заявлено.
```

## Почему

Честная область свидетельства позволяет следующему участнику принять остаточный риск и выбрать недостающую проверку.

## Когда применять

Для любых итогов работы. Отчет может быть коротким; не требуется хранить полный лог, если достаточно команды, результата и безопасной ссылки. Внешняя спецификация подтверждается документальным review, а не выдуманным запуском.

### Подробные условия

Различай passed, failed, flaky, skipped, not-run и blocked; причины пропуска и блокировки видимы. Если часть набора не выполнена, общий вывод не должен утверждать полную приемку.

Статическая проверка, compilation, тест поведения и ручной осмотр подтверждают разные свойства. Проверка формата Markdown не доказывает правильность нормы, работу публикации или соответствие проекта-потребителя. После изменения объекта старый успешный отчет подтверждает только старую версию.

## Как проверить

- Проверка запущена на C → сформировать отчет → объект, среда и фактический результат известны.
- Часть тестов пропущена или первый прогон нестабилен → сформировать итог → skipped/flaky видны, полного passed нет.
- Проверены только документы → описать результат → отсутствует заявление о runtime и публикации потребителя.

## Человек

Принимает результат с учетом видимых ограничений и остаточного риска.

## Агент

Различает run, source-reviewed, manual-reviewed и not-run; не пишет «проверено», не уточнив что и как.
