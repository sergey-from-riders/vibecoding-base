# Pull request

## Коротко

Изменение должно решать одну объяснимую задачу и содержать все нужное для ее проверки: код, соответствующие тесты, контракт и документацию.

## Плохо

```text
Один PR: исправление доступа, переименование всех файлов,
новая библиотека, форматирование и несвязанный новый экран.
```

## Хорошо

```text
Цель: ограничить чтение счета его tenant.
Diff: проверка доступа, регрессия, уточнение контракта ошибки.
Отдельный PR: механическое переименование после этого изменения.
Зависимый шаг: указан base ref и проверена совместимая последовательность.
```

## Почему

Связная область дает ревьюеру возможность установить причину каждой правки и локализовать регрессию, не разрывая обязательный контракт на нерабочие части.

## Когда применять

Для изменений любого размера. Массовая генерация или перенос может быть связным большим diff; укажи источник, способ воспроизведения и выборочную проверку смысла. Здесь не требуется внедрять генератор.

### Подробные условия

В описании укажи цель, границы diff, зависимости и риск. Число строк само по себе не определяет размер задачи.

Большую работу разделяй по совместимым промежуточным состояниям. Для зависимых PR укажи базу и порядок; каждый шаг проверяется относительно своей объявленной базы и не оставляет основную ветку неработоспособной при принятом порядке. Связное массовое переименование допустимо отдельным изменением с механической проверкой; не смешивай его с изменением поведения.

## Как проверить

- Одна задача → сопоставить каждый измененный файл с целью → несвязанные правки вынесены или обоснованы.
- Два зависимых PR → проверить порядок на заявленных базах → промежуточные состояния допустимы.
- Массовое переименование → проверить импорты/ссылки и отсутствие смены поведения → большой diff принят без искусственного лимита строк.

## Человек

Выбирает границу изменения, которую можно содержательно проверить.

## Агент

Показывает зависимости и не добавляет попутные рефакторинги, не нужные для задачи.
