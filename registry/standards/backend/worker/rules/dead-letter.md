# Dead-letter queue

## Коротко

Сообщение, которое нельзя обработать в установленном бюджете попыток, должно перейти в устойчивый разбор с причиной, владельцем и ограниченным повторным запуском.

## Плохо

```text
Некорректное сообщение бесконечно повторяется.
В DLQ нет владельца; сообщения исчезают по retention до разбора.
```

## Хорошо

```text
Временные ошибки: bounded retry/backoff.
Невосстановимая ошибка или исчерпан бюджет → DLQ/quarantine.
Сохраняются operation_key, безопасная причина, attempts и время.
После исправления — авторизованный redrive с лимитом скорости.
```

## Почему

DLQ изолирует проблемную работу, но сам не исправляет ее. Повтор с новым transport ID не должен менять бизнес-идентичность и обходить дедупликацию. Полный payload может содержать секреты: доступ к очереди разбора ограничен, диагностика минимальна.

## Когда применять

Для устойчивых очередей с повтором; отдельная DLQ — один способ, допустима таблица quarantine с теми же гарантиями. Задайте max attempts/общий срок, retention, наблюдение за числом и возрастом, владельца и критерий закрытия. Для permanent-сбоев возможен ранний quarantine без бесполезного retry.

У Amazon SQS maxReceiveCount считает получения; retention standard DLQ связан с исходным временем постановки, FIFO имеет другую семантику. Проверьте достаточно ли времени на разбор. Если операции требуют строгого порядка, пропуск через DLQ может его нарушить: выберите остановку группы/компенсацию, не продолжайте зависимые события вслепую. Redrive разрешается после устранения причины, сначала ограниченной партией, с сохранением исходного operation_key и наблюдением дубликатов.

## Как проверить

1. Временный отказ → повтор в бюджете → обработка завершена без DLQ → attempts и один эффект.

2. Поврежденное сообщение → конечное число попыток → устойчивый quarantine и сигнал владельцу, независимые группы продолжаются → DLQ и метрики.

3. Причина исправлена → повтор ограниченной партии, включая completed operation → эффект ровно один, порядок выбранной группы сохранен/явно восстановлен → журнал redrive и бизнес-состояние.

## Человек

Назначает владельца разбора, retention, политику порядка и полномочия redrive.

## Агент

Проверяет конечность попыток, сохранность причины и operation_key, доступ и скорость повторного запуска.
