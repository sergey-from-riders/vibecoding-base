# Границы backend

## Коротко

Отделяйте транспортный разбор и представление ответа от повторно используемых правил приложения. Граница нужна там, где есть самостоятельная ответственность или второй потребитель.

## Плохо

```text
HTTP handler декодирует JSON, считает скидку, выполняет SQL
и синхронно отправляет письмо внутри той же функции.
```

## Хорошо

```text
HTTP adapter: декодирование, контекст пользователя, HTTP-ответ.
CreateOrder: инварианты и граница транзакции.
Repository: SQL, без зависимости от HTTP.
Письмо: сохраненное outbox-событие; обработчик повторяемый.
```

## Почему

CreateOrder здесь — функция/компонент внутри процесса, не обязательный микросервис. Названия service/repository не являются требованием Go. Организация модулей Go поддерживает пакеты и internal; она не предписывает три слоя. Разделение оправдано возможностью проверить расчет без сети и вызвать ту же операцию из worker.

## Когда применять

Для backend с нетривиальными правилами, несколькими transport-адаптерами или внешними эффектами. Направление зависимостей должно быть явным: бизнес-расчет не импортирует HTTP response writer; адаптер передает проверенную личность и данные, а приложение обеспечивает бизнес-полномочия/инвариант. Один слой владеет commit/rollback всей операции; repository не коммитит отдельно каждый шаг вопреки этой границе.

Маленький read-only CRUD допустимо реализовать одной короткой функцией без формальных интерфейсов и пустых прокси. Вынесение интерфейса нужно потребителю/замене зависимости, а не каждой структуре. Количество вызовов service в handler не нормируется. Смена архитектуры не должна молча менять HTTP или транзакционные гарантии.

## Как проверить

1. Правило скидки → вызов без HTTP/реальной БД → предсказуемый результат → изолированный тест функции.

2. HTTP и worker создают заказ → общий application-вызов → одинаковые бизнес-проверки и одна транзакция → тест двух адаптеров.

3. Малый endpoint чтения либо ошибка второго шага записи → ревью/выполнение → нет фиктивных слоев; для записи полный rollback → зависимости и состояние БД.

## Человек

Определяет бизнес-инварианты, потребителей и владельца транзакции.

## Агент

Выделяет только обоснованные границы, проверяет направление imports и повторное использование без transport-зависимостей.
