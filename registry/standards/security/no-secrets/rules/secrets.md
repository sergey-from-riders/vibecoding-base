# Управление секретами

## Коротко

Секреты имеют владельца, минимальные права, среду, срок и процедуру отзыва. Они поступают в runtime через предназначенный для этого механизм и не попадают в репозиторий, клиент или диагностику.

## Плохо

```text
API_KEY = "действующий секрет" в исходниках, build args или frontend bundle.
Удалили строку из последнего commit и объявили утечку устраненной.
```

## Хорошо

```text
secret reference → разрешенная runtime identity → secret store.
Реестр: owner, environment, purpose, permissions, expiry/rotation policy.
Ротация: новый key → проверенные consumers → отзыв старого → проверка отказа.
При утечке: ограничить/отозвать доступ, затем устранить опубликованные копии.
```

## Почему

Удаление текста не отзывает полномочия уже скопированного ключа. Секреты могут сохраниться в истории Git, слоях образа, CI log, crash dump и кеше сборки. Переменная окружения — способ доставки, а не гарантия конфиденциальности: ее тоже можно вывести или встроить в клиентский артефакт.

## Когда применять

Для API credentials, private keys, connection strings, webhook secrets и других bearer-полномочий. Публичные идентификаторы и явно publishable keys не являются секретом по одному названию; классифицируйте их по возможностям. Предпочитайте workload identity/короткоживущие credentials, где поддерживается; статическим задайте owner, область, среду, доступ и проверяемый lifecycle. Это правило не требует периодически менять пользовательские пароли без основания.

Разделяйте dev/test/live, сервисы и права чтения/изменения. Секреты не передаются в клиентскую сборку, URL, промпты, issue и логи; .env.example содержит только placeholders. Secret store недоступен — не заменяйте значение встроенным production fallback. Отсутствующий обязательный секрет останавливает соответствующую операцию/запуск.

Плановая ротация учитывает несколько экземпляров: если провайдер допускает overlap, введите новый key, переключите consumers, подтвердите работу и отзовите старый к сроку. Если overlap невозможен, документируйте согласованное окно/перезапуск; компрометация может требовать немедленного отзыва. Проверка старого ключа проводится уполномоченным владельцем в контролируемом тесте без публикации значения.

Scanner finding означает подозрение, а не доказанный доступ. Триаж фиксирует путь/тип/срок и владельца без секрета; чужую найденную credential нельзя пробовать в сервисе для «проверки». Подтвержденный или вероятно раскрытый рабочий секрет отзывают/заменяют, затем чистят копии и предотвращают повтор. Очистка истории не заменяет отзыв.

## Как проверить

1. Runtime identity с минимальными правами → получение нужного секрета → работа только в своей среде → audit доступа и отсутствие значения в артефактах.

2. Плановая ротация на нескольких экземплярах → переключение и отзыв → новые работают, старый больше не принимается → безопасное свидетельство владельца.

3. Scanner находит placeholder либо вероятный live secret; store недоступен → триаж/запуск → значения не публикуются, без самовольной проверки доступа; нет небезопасного fallback → запись решения.

## Человек

Назначает владельцев, права, сроки, аварийный отзыв и допустимое окно ротации.

## Агент

Использует references и placeholders; проверяет сборочные/логовые каналы, триаж и lifecycle без раскрытия или самовольного использования credential.
