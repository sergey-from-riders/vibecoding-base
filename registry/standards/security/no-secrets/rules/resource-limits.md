# Лимиты ресурсов

## Коротко

Для дорогой операции задайте проверяемые бюджеты частоты, конкурентности, объема и стоимости. Ограничение одного HTTP endpoint не ограничивает суммарную работу его дочерних задач.

## Плохо

```text
Каждый pod допускает 100 запросов в минуту по IP.
Запрос создает неограниченное число фоновых jobs и распаковывает весь body.
```

## Хорошо

```text
Профиль export: квота tenant + actor, общий бюджет сервиса.
Атомарный admission до создания job; ограничены очередь и workers.
Лимиты rows/bytes/runtime, отмена и освобождение занятого слота.
Отказ rate limit → 429; oversize body → 413; причина безопасна.
```

## Почему

Одинаковый лимит на каждом из N экземпляров допускает N-кратный общий расход. IP за NAT не равен пользователю, а доверие к произвольному forwarded header позволяет менять ключ. Дешевая постановка задания может породить дорогие SQL, файловые операции или платные вызовы — учет должен происходить до этого эффекта.

## Когда применять

Для публичных и внутренних недоверенных запросов, batch/GraphQL, uploads, экспорта, AI/API/SMS и фоновых работ. Проект указывает единицы, окно/burst, максимальную конкурентность, предел очереди, тело до/после распаковки, число элементов/строк и общий deadline. Авторизованный actor/tenant дополняется общим бюджетом; для анонимных действий применяйте отдельную политику IP/устройства/назначения. Forwarded IP доверяется только известному proxy.

Глобальные денежные и ресурсные квоты требуют атомарного reserve/commit/release либо доказанного эквивалента с ограниченной погрешностью. Повторы той же платной операции не резервируют бюджет бесконечно; crash/timeout освобождает или сверяет резерв по явно заданному lifecycle. Для concurrency учитывайте окончание реальной работы, а не только ответ enqueue.

HTTP-профиль: 429 для превышения частоты, 413 для слишком большого content; Retry-After передается, когда сервер может указать полезное время, и не является обязательным по RFC. Постоянная бизнес-квота получает отдельный код/описание условия восстановления, а не бесконечное «повторите через секунду». При перегрузке допускается отказ раньше HTTP-обработчика. Определите поведение при outage limiter: дорогие/денежные операции закрываются либо используют заранее ограниченный резерв; дешевое чтение может иметь документированный локальный fallback. Unbounded fail-open запрещен для защищаемого бюджета.

## Как проверить

1. N экземпляров одновременно расходуют остаток квоты → admission → суммарный расход не превышает предел/объявленную погрешность → общий счетчик и эффекты.

2. Burst, oversize/compressed body и batch с большим fan-out → запрос → ранний ограниченный отказ, 429/413 по профилю, очередь не растет без предела → HTTP/метрики.

3. Хранилище лимитов недоступно, worker падает, окно истекает → новые операции/recovery → соблюден fallback, резервы восстановлены и нормальная работа возобновляется → тест lifecycle.

## Человек

Назначает бюджеты по стоимости и SLO, допустимый burst, восстановление квоты и политику outage.

## Агент

Проверяет учет на нескольких экземплярах, входные размеры, background fan-out и освобождение/сверку резервов.
