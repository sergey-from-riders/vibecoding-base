# Офлайн-синхронизация

## Коротко

Отделяйте локальный черновик от подтвержденного сервером изменения. Для отложенной записи сохраняйте устойчивую операцию, владельца, зависимости и правила разрешения конфликта до попытки синхронизации.

## Плохо

```text
Очередь хранится только в памяти.
При reconnect каждой записи присваивается новый idempotency key.
После смены аккаунта старая очередь уходит с новым access token.
Любой конфликт перезаписывается последней локальной копией.
```

## Хорошо

```text
Локальная транзакция: обновить черновик + сохранить операцию для аккаунта A.
У операции неизменный ключ, исходная версия объекта и зависимость от создания.
Перезапуск -> та же операция, тот же ключ, то же состояние результата.
Синхронизация -> актуальная авторизация A -> безопасный повтор/сверка.
Конфликт версии -> сохранить черновик и показать согласованный выбор.
Смена аккаунта -> остановить очередь A; она не отправляется от имени B.
```

## Почему

Сеть может исчезнуть после успешной серверной записи, но до получения ответа. Локальное «не отправлено» в таком случае не доказывает отсутствие эффекта. Без привязки к аккаунту и версии восстановление сети может привести к дубликату или потере чужих данных.

## Когда применять

Мобильные приложения с офлайн-записью; поддержка только чтения не требует очереди команд. Выберите durable-хранилище и по возможности атомарно сохраняйте локальное изменение вместе с намерением отправки. Когда атомарность недоступна, опишите восстановление незавершенной пары.

Устойчивый ключ действует в согласованном серверном контракте идемпотентности, включая срок хранения и совпадение payload. Если сервер такой гарантии не дает, добавьте сверку или запрет опасного автоматического повтора; клиентский UUID сам по себе ее не создает.

Сохраняйте зависимости: изменение еще не созданного объекта не отправляется раньше его создания. Состояние unknown после таймаута отличается от ошибки валидации. После 401/403 остановите соответствующие операции и потребуйте восстановление доступа; не повторяйте бесконечно.

Политика конфликта зависит от предметной области: серверная версия/ETag, ручное объединение или ограниченный автоматический merge. «Последняя запись по часам телефона побеждает» не универсальна. Удаление учитывается как удаление, а не повод воскресить старую копию. Задайте срок хранения черновиков, очереди и tombstones, очистку персональных данных при logout и поведение, если пользователь хочет сохранить несинхронизированный черновик.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Офлайн-изменение, kill процесса, запуск | Черновик и операция восстановлены с тем же ключом | Осмотр durable-состояния |
| Сервер применил запись, ответ потерян | Повтор по контракту или сверка; нет нового эффекта с новым ключом | Серверный журнал и клиентская очередь |
| Создание и зависимое обновление | Порядок соблюден, временный ID заменен согласованно | Последовательность операций |
| Сервер изменен/удален другим клиентом | Конфликт обработан без молчаливой потери или восстановления удаления | Два клиента и сохраненный черновик |
| Logout, новый аккаунт, истекшие права и срок хранения | Старая очередь не отправляется новым пользователем; данные очищены по политике | Тест аккаунтов и retention |

Наличие сетевого сигнала не доказывает доступность API или действительность сессии.
