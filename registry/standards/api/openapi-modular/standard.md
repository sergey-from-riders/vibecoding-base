## HTTP-статусы

### Коротко

HTTP-код передаёт результат запроса клиенту, прокси и мониторингу. При ошибке запроса возвращайте подходящий 4xx или 5xx; поле в JSON не заменяет HTTP-код.

### Плохо

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status":404,"message":"Не найдено"}
```

### Хорошо

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"title":"Не найдено"}
```

### Почему

Клиентская библиотека и инфраструктура могут принять ошибку с кодом 200 за успешный запрос. В хорошем примере отсутствующий ресурс обозначен HTTP-кодом 404. Поля `type` и `status` не нужны для демонстрации этого различия.

### Когда применять

Для HTTP API; семантика кодов определяется RFC 9110. Успешное чтение заказа со значением `status: "cancelled"` остаётся успешным HTTP-запросом: это состояние заказа, а не ошибка доставки его представления.

В Problem Details по RFC 9457 поле `status` необязательно. Оно полезно, когда тело сохраняется без HTTP-метаданных или нужно установить исходный код после изменения ответа посредником. Если исходный сервер включает это числовое поле, оно должно совпадать с отправленным HTTP-кодом. Расхождение, возникшее после прокси, диагностируют отдельно; клиент не подменяет HTTP-код значением из тела.

При отсутствии `type` используется `about:blank`. `title` — пояснение для человека, а не машинный код ошибки. Для 4xx/5xx RFC 9110 рекомендует объясняющее тело; это не требование всегда возвращать JSON. Ответ на HEAD не содержит тела, клиент обрабатывает ошибку и при пустом или нераспознаваемом ответе.

Состав примера — редакционный выбор. Перед удалением `status` из работающего API проверьте OpenAPI, сериализаторы и клиентов: необязательное поле формата может быть обязательным в конкретном контракте.

### Как проверить

- Запрос отсутствующего ресурса возвращает 404; ответ origin с `status: 404` и без поля корректно обрабатывается клиентом.
- Если origin отправляет HTTP 404 и `status: 200`, контрактный тест фиксирует несовпадение. При расхождении после прокси сравниваются исходный и полученный ответы.
- Ответ 4xx/5xx без тела или с неизвестным форматом не превращается в успех и не вызывает необработанную ошибку JSON-парсера.
- HEAD отсутствующего ресурса возвращает подходящий HTTP-код без тела.
- Чтение отменённого заказа возвращает 200 с его бизнес-состоянием; удаление поля из существующего контракта проверяется на поддерживаемых клиентах.

### Человек

Определяет бизнес-смысл результата и требования совместимости клиентов. Выбирает, нужен ли `status` в теле конкретного API.

### Агент

Проверяет HTTP-код, формат и тело отдельно на исходном сервере и после посредников. Фиксирует результаты сценариев; не удаляет поле только ради сокращения JSON.

### Источники

- [RFC 9110: HTTP Semantics, разделы 9.3.2, 15.5 и 15.6](https://www.rfc-editor.org/rfc/rfc9110.html)
- [RFC 9457: Problem Details, разделы 3.1 и 3.1.2](https://www.rfc-editor.org/rfc/rfc9457.html)

Уровень: Обязательно. Опубликовано: 2026-11-09. Проверено: 2026-11-13.

## HTTP-методы

### Коротко

GET и HEAD читают; изменение бизнес-состояния должно иметь соответствующий метод.

### Плохо

```http
GET /orders/42/delete
```

### Хорошо

```http
DELETE /orders/42
```

### Почему

Ссылку может заранее открыть браузер, робот или прокси.

### Когда применять

POST подходит для команд и создания, PUT — полного идемпотентного замещения, PATCH — частичного изменения. Семантику повторов PATCH нужно описывать.

### Как проверить

- Открытие обычной ссылки не удаляет и не оплачивает данные?

### Человек

Согласует назначение операции и последствия повторного запроса.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Открытие обычной ссылки не удаляет и не оплачивает данные?

- [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)
- [rfc5789.html](https://www.rfc-editor.org/rfc/rfc5789.html)

## Problem Details

### Коротко

Ошибка API содержит понятное объяснение и стабильный идентификатор типа. Внутренние пути, SQL и секреты не включаются в публичный ответ.

### Плохо

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{"error":"SQL exception at /private/app/main.go:42"}
```

### Хорошо

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{"type":"https://example.com/problems/validation",
 "title":"Ошибка проверки данных",
 "errors":[{"pointer":"/email","code":"invalid_format",
            "message":"Укажите корректный email"}]}
```

### Почему

Оба примера описывают ошибку проверки полей. Хороший пример сообщает, что исправить, и не раскрывает реализацию. Клиент распознаёт тип по `type`, а не разбирает локализуемый текст `title` или `message`. URI в примере вымышленный; проект назначает собственный стабильный идентификатор.

### Когда применять

Для HTTP API, выбравших RFC 9457. Ответ с JSON Problem Details использует `application/problem+json`. Стандартные поля формата необязательны; их набор в примере не является списком обязательных полей RFC.

`type` идентифицирует тип проблемы; при отсутствии подразумевается `about:blank`. `title` кратко описывает тип и может локализоваться; `detail`, если присутствует, поясняет конкретный случай. Машинная логика не должна зависеть от текста этих полей.

`errors` — расширение данного API. Здесь `pointer` указывает на поле исходного JSON по RFC 6901, `code` — стабильный проектный код проверки, `message` — текст для человека. Имена, типы и обязательность этих полей фиксируются в OpenAPI проекта; другой API может выбрать другое расширение.

`status` можно включить по условиям связанного правила HTTP-статусов. Не удаляйте поля существующего контракта без проверки клиентов. Неизвестные расширения клиент игнорирует. Стандартное поле с типом, не соответствующим RFC, обрабатывается как отсутствующее; это не отменяет валидацию на стороне генератора ответа.

### Как проверить

- Некорректный email: ответ содержит выбранный 4xx, правильный media type и описание, позволяющее исправить поле.
- Смена языка меняет сообщение, но сохраняет `type` и проектный `code`; клиент продолжает распознавать ошибку.
- Новое неизвестное расширение не ломает старого клиента. Отсутствие необязательного `status` тоже не ломает клиент, если его контракт не требует это поле.
- Неверный тип стандартного поля, например строковый `status`, не вызывает сбой клиента: поле игнорируется, HTTP-код остаётся доступен. Серверная проверка контракта выявляет такой ответ как дефект генератора.
- Публичный ответ не содержит SQL, внутренних путей, токенов и лишних персональных данных; подробная диагностика хранится в защищённом журнале.

### Человек

Определяет публичные типы ошибок, локализацию и допустимые детали. Принимает контракт расширений и сроки совместимости.

### Агент

Реализует и проверяет сериализацию, media type, локализацию и обработку неизвестных полей. Отдельно фиксирует выполненные тесты и предложенные сценарии.

### Источники

- [RFC 9457: Problem Details, разделы 3.1, 3.2 и 5](https://www.rfc-editor.org/rfc/rfc9457.html)
- [RFC 6901: JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901.html)

Уровень: Рекомендуется. Опубликовано: 2026-11-09. Проверено: 2026-11-13.

## OpenAPI-контракт

### Коротко

В контракте должны быть реальные методы, схемы, ошибки, доступ и примеры.

### Плохо

```text
Новый endpoint работает, но в документации его нет.
```

### Хорошо

```text
Изменены обработчик, OpenAPI, пример и тест.
operationId уникален и стабилен.
```

### Почему

Клиенты и агенты не должны угадывать формат запроса.

### Когда применять

OpenAPI 3.2 подходит при поддержке инструментов; 3.1 остаётся допустимым осознанным выбором. Разбиение по модулям зависит от размера API.

### Как проверить

- Сопоставьте реальные маршруты, операции контракта и каталог endpoints.

### Человек

Утверждает публичные поля и обязательства перед клиентами.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Сопоставьте реальные маршруты, операции контракта и каталог endpoints.

### Источники

- [OpenAPI Specification v3.2.0](https://spec.openapis.org/oas/v3.2.0.html)

## Идемпотентность API

### Коротко

После потери ответа повторный запрос не должен создавать вторую оплату или заказ.

### Плохо

```text
Тайм-аут → новый requestId → повторное списание.
```

### Хорошо

```text
Тайм-аут → тот же Idempotency-Key.
Сервер узнаёт операцию и возвращает её результат.
```

### Почему

Сетевой тайм-аут не сообщает, успел ли сервер выполнить действие.

### Когда применять

Ключ связан с пользователем, операцией и содержимым. Другое содержимое под тем же ключом — конфликт. Срок хранения ключей документируется. `Idempotency-Key` — контракт конкретного API, а не обязательный заголовок RFC 9110. После истечения срока дедупликации повтор может стать новой операцией.

### Как проверить

- Повторите запрос одновременно и после потери ответа.

### Человек

Определяет, что считать одной операцией и как долго хранить её результат.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Повторите запрос одновременно и после потери ответа.

### Источники

- [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)
- [Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

## Оптимистическая блокировка

### Коротко

Проверяйте версию записи перед сохранением, если пользователь может перезаписать чужую работу.

### Плохо

```text
Аня и Борис открыли v3.
Аня сохранила v4. Борис молча затёр её.
```

### Хорошо

```text
Борис отправляет If-Match: "v3".
Сервер отвечает 412: версия уже изменилась.
```

### Почему

Последняя запись не всегда является правильным результатом совместной работы.

### Когда применять

Можно использовать ETag/If-Match либо документированный revision с 409. Не смешивайте эти договорённости неявно.

### Как проверить

- Два клиента меняют одну запись: второй получает понятный конфликт?

### Человек

Выбирает поведение интерфейса при конфликте изменений.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Два клиента меняют одну запись: второй получает понятный конфликт?

## Пагинация

### Коротко

Договоритесь о размере страницы, сортировке, фильтрах и продолжении списка.

### Плохо

```text
GET /users → вся таблица без лимита.
```

### Хорошо

```text
GET /users?limit=50&cursor=...
Ответ: items и next_cursor.
```

### Почему

Неограниченная выдача расходует память и делает время ответа непредсказуемым.

### Когда применять

Cursor удобен для меняющихся списков; offset допустим для небольших стабильных выборок. Порядок должен иметь уникальный tie-breaker.

### Как проверить

- Проверьте предел размера и повторяющиеся значения сортировки.

### Человек

Определяет порядок списка, лимит страницы и требования к стабильности выдачи.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Проверьте предел размера и повторяющиеся значения сортировки.

### Источники

## Совместимость API

### Коротко

Удаление поля или изменение его смысла требует совместимости со старыми клиентами.

### Плохо

```text
amount вчера означал рубли, сегодня — копейки.
```

### Хорошо

```text
Новое поле amount_minor.
Старое поддерживается на время перехода.
```

### Почему

Клиент может продолжить работать без ошибки, но с неверными данными.

### Когда применять

Срок перехода согласуется с потребителями. 90 дней — возможная политика проекта, а не универсальное требование протокола.

### Как проверить

- Старый клиент проходит контрактные тесты новой версии?

### Человек

Определяет поддерживаемых клиентов и срок перехода на новый контракт.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Старый клиент проходит контрактные тесты новой версии?

## HTTP-заголовки

### Коротко

Статус, формат содержимого и кеширование описываются стандартными средствами HTTP.

### Плохо

```http
HTTP 200
X-App-Result: error
```

### Хорошо

```http
HTTP 503 Service Unavailable
Retry-After: 30
Content-Type: application/problem+json
```

### Почему

Собственный заголовок не заменяет стандартную семантику.

### Когда применять

X-Request-Id полезен для поддержки, если согласован. X-App-Result, X-App-Action и X-App-Validate не обязательны для всех API. Content-Language указывают по смыслу представления.

### Как проверить

- Работает ли обычный HTTP-клиент без знания собственных заголовков?

### Человек

Согласует требования клиентов, прокси и трассировки.

### Агент

Реализует серверный контракт и проверяет успешный запрос, неверный ввод и повторное обращение.

Контроль результата:

- Работает ли обычный HTTP-клиент без знания собственных заголовков?
