# HTTP-статусы

## Коротко

HTTP-код передаёт результат запроса клиенту, прокси и мониторингу. При ошибке запроса возвращайте подходящий 4xx или 5xx; поле в JSON не заменяет HTTP-код.

## Плохо

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status":404,"message":"Не найдено"}
```

## Хорошо

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"title":"Не найдено"}
```

## Почему

Клиентская библиотека и инфраструктура могут принять ошибку с кодом 200 за успешный запрос. В хорошем примере отсутствующий ресурс обозначен HTTP-кодом 404. Поля `type` и `status` не нужны для демонстрации этого различия.

## Когда применять

Для HTTP API; семантика кодов определяется RFC 9110. Успешное чтение заказа со значением `status: "cancelled"` остаётся успешным HTTP-запросом: это состояние заказа, а не ошибка доставки его представления.

В Problem Details по RFC 9457 поле `status` необязательно. Оно полезно, когда тело сохраняется без HTTP-метаданных или нужно установить исходный код после изменения ответа посредником. Если исходный сервер включает это числовое поле, оно должно совпадать с отправленным HTTP-кодом. Расхождение, возникшее после прокси, диагностируют отдельно; клиент не подменяет HTTP-код значением из тела.

При отсутствии `type` используется `about:blank`. `title` — пояснение для человека, а не машинный код ошибки. Для 4xx/5xx RFC 9110 рекомендует объясняющее тело; это не требование всегда возвращать JSON. Ответ на HEAD не содержит тела, клиент обрабатывает ошибку и при пустом или нераспознаваемом ответе.

Состав примера — редакционный выбор. Перед удалением `status` из работающего API проверьте OpenAPI, сериализаторы и клиентов: необязательное поле формата может быть обязательным в конкретном контракте.

## Как проверить

- Запрос отсутствующего ресурса возвращает 404; ответ origin с `status: 404` и без поля корректно обрабатывается клиентом.
- Если origin отправляет HTTP 404 и `status: 200`, контрактный тест фиксирует несовпадение. При расхождении после прокси сравниваются исходный и полученный ответы.
- Ответ 4xx/5xx без тела или с неизвестным форматом не превращается в успех и не вызывает необработанную ошибку JSON-парсера.
- HEAD отсутствующего ресурса возвращает подходящий HTTP-код без тела.
- Чтение отменённого заказа возвращает 200 с его бизнес-состоянием; удаление поля из существующего контракта проверяется на поддерживаемых клиентах.

## Человек

Определяет бизнес-смысл результата и требования совместимости клиентов. Выбирает, нужен ли `status` в теле конкретного API.

## Агент

Проверяет HTTP-код, формат и тело отдельно на исходном сервере и после посредников. Фиксирует результаты сценариев; не удаляет поле только ради сокращения JSON.
