# OpenAPI-контракт

## Коротко

Если проект использует OpenAPI, контракт должен описывать фактически поддерживаемые операции, вход, ответы и доступ; проверка структуры документа не заменяет проверку сервера.

## Плохо

```yaml
GET /health реализован, но отсутствует в контракте.
Клиент генерируется по вымышленному ответу.
```

## Хорошо

```yaml
openapi: 3.1.1
info: {title: Example API, version: 1.0.0}
paths:
  /health:
    get:
      operationId: getHealth
      security: []
      responses:
        '204':
          description: Process is responding
```

## Почему

Пример — полный минимальный документ для публичного GET /health без тела. security: [] явно снимает требования аутентификации для операции; это не образец доступа к пользовательским данным. operationId в OAS опционален; при наличии он обязан быть уникальным среди операций. Обязательное наличие и стабильность для генерации клиентов или каталога — выбранный профиль проекта.

## Когда применять

Выберите поддерживаемую инструментами версию OAS: семейство 3.1 допустимо, 3.2 применяется после проверки parser/generator/validator проекта. Не объявляйте показанный patch-релиз последним. Разделение файлов и $ref нужны только при пользе для сопровождения.

Для каждой операции задайте path/method, параметры, required и null по смыслу, requestBody и media type при наличии тела, ответы успеха и существенных ошибок, схемы и security. Входные и выходные примеры должны соответствовать своим схемам. Не выдумывайте тело для 204/HEAD. Новые поля и статусы проходят api.compatibility. Различайте три проверки: lint/resolve документа, соответствие реального HTTP и совместимость потребителей.

## Как проверить

1. Реальный маршрут GET /health → запрос → 204 без тела, совпадающий с описанием → трасса и сопоставление операций.

2. Ошибочный пример или неразрешимый $ref → проверка контракта → конкретная ошибка до генерации клиента → отчет валидатора.

3. Запрос к защищенной операции без credentials и старый SDK → сервер и контракт дают согласованные ответы и совместимость → интеграционные/контрактные результаты отдельно от lint.

## Человек

Определяет публичный контракт, поддерживаемые клиенты и используемую версию инструментов.

## Агент

Обновляет операцию, примеры и security вместе с реализацией; фиксирует отдельно результат lint, HTTP-проверки и совместимости.
