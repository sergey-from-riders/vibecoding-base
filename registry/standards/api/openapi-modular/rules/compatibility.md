# Совместимость API

## Коротко

Сохраняйте синтаксис и смысл контракта для поддерживаемых клиентов. Валидный JSON и добавление необязательного поля сами по себе не доказывают совместимость.

## Плохо

```text
v1: {"amount": 123.45}  // RUB
v1 после изменения: {"amount": 12345}  // копейки
```

## Хорошо

```text
v1 в период миграции: {"amount": 123.45, "amount_minor": 12345}
Старый клиент продолжает читать amount в RUB.
Новый клиент читает amount_minor в копейках.
Удаление amount — только после завершения поддержки v1.
```

## Почему

Сравнивайте wire-формат, сгенерированные SDK и бизнес-смысл. AIP-180 — руководство Google для их API, применяемое здесь как основание рекомендаций, а не универсальная спецификация HTTP.

| Изменение | Проверка до выпуска |
| --- | --- |
| Удаление/переименование, optional → required в запросе | Старый запрос больше не принимается; нужен переход |
| Тип, единица, формат, null вместо значения или отсутствие | Десериализация и смысл у старого клиента |
| Новое поле ответа или значение enum | Поведение строгого декодера и неизвестного значения |
| Новый HTTP status, порядок, значения по умолчанию | Ветки клиента и наблюдаемое поведение |

## Когда применять

Для API с независимо обновляемыми потребителями. Зафиксируйте список поддерживаемых версий/клиентов, владельцев и критерий завершения миграции: подтверждение перехода либо истечение опубликованного периода поддержки. 90 дней не является общей нормой. Для совместно выпускаемых внутренних компонентов допустим координированный несовместимый релиз с проверенным порядком развертывания.

Не удаляйте поля только как «дублирование»: проверьте потребителей. Новое поле добавляется, только если у него есть назначение и определены тип, обязательность, единицы и отсутствие/null. В примере оба поля представляют одну сумму и вычисляются согласованно.

## Как проверить

1. Сохраненные запросы и клиент предыдущей поддерживаемой версии → новый сервер → прежний смысл и успешная десериализация → контрактные fixtures и результаты клиента.

2. amount меняет единицу или обязательное поле удалено → diff и старый клиент → изменение блокируется как несовместимое → конкретный failing case.

3. Новый enum/поле и отсутствующее/null значение → старый строгий декодер → поведение соответствует согласованной политике; иначе версия/миграция → отчет совместимости.

## Человек

Определяет поддерживаемых потребителей и критерий снятия старого контракта.
