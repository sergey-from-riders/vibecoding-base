# Идемпотентность API

## Коротко

Для повторяемой команды с риском двойного эффекта задайте идентичность операции, атомарную дедупликацию и восстановление неопределенного результата.

## Плохо

```text
POST оплаты → провайдер списал, ответ потерян.
Клиент создал новый ключ → второе списание.
```

## Хорошо

```text
Одна оплата: ключ K в области tenant + операция.
Атомарно резервируем K и fingerprint входа: pending.
Эффект и результат фиксируем вместе, если они в одной БД.
Повтор K с тем же входом получает прежний результат.
Внешний эффект: тот же ключ провайдера + сверка при сбое.
```

## Почему

Уникальный request ID для трассировки не обязательно является ключом одной бизнес-операции. RFC 9110 определяет идемпотентность метода, но не навязывает Idempotency-Key. У Stripe API v1 и API v2 различается обработка сохраненных ошибок; поведение провайдера нельзя автоматически переносить в собственный API.

## Когда применять

Для создания заказа, платежа и других команд, которые клиент вправе повторить. Контракт задает область ключа, сравнение содержимого, срок хранения и ответы для pending/completed/failed. Сначала проверяйте полномочия: ключ не дает доступа к чужому результату. Иное содержимое под тем же ключом отклоняется до эффекта. Два одновременных запроса не должны оба получить право выполнения.

Определите, какие ошибки сохраняются и какие допускают повтор; ошибка валидации до начала эффекта не должна оставлять вечный pending. Истекший TTL может разрешить новый эффект: срок обязан покрывать договоренный период повторов. Сбой после внешнего эффекта не разрешает удалить pending и начать заново вслепую: восстановите результат по прежнему ключу/ID или выполните сверку. Локальная БД и внешний API не образуют одну транзакцию.

## Как проверить

1. Два одновременных запроса с K и одинаковым входом → резервирование → один эффект, второй ожидает или получает документированный pending/результат → запись ключа и бизнес-объект.

2. K уже принят → иной payload либо другой пользователь → конфликт/отказ без раскрытия результата → HTTP-ответ и неизменные данные.

3. Провайдер применил команду, процесс упал до записи результата → повтор K и восстановление → один внешний эффект, локальный результат подтвержден сверкой → provider ID и журнал восстановления.

4. Ключ истек → повтор → поведение соответствует TTL-контракту; клиент не объявляет новую операцию безопасным retry → тест времени хранения.

## Человек

Определяет границу одной операции, период повторов и процесс разбора неопределенного исхода.

## Агент

Реализует уникальность резервирования, состояния и восстановление; проверяет два процесса и сбой после эффекта.
