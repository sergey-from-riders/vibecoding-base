# Оптимистическая блокировка

## Коротко

Если конкурирующее редактирование может потерять изменения, сравнивайте версию и изменяйте запись атомарно. Одна предварительная проверка перед отдельным UPDATE недостаточна.

## Плохо

```text
А и Б прочитали v3.
А проверил v3; Б проверил v3.
Оба отдельно записали новую версию: изменение А потеряно.
```

## Хорошо

```text
GET /documents/42 → ETag: "v3"
А: PATCH с If-Match: "v3" → атомарная запись v4.
Б: PATCH с If-Match: "v3" → 412, запись не изменена.
Б получает v4 и предлагает пользователю сравнение изменений.
```

## Почему

Сравнение и запись должны выполняться одним условным UPDATE или внутри подходящей блокировки/транзакции. В HTTP-варианте If-Match использует сильное сравнение ETag; W/"v3" не подходит. Валидатор должен меняться при изменении представления и учитывать его варианты. Простое имя версии не делает ETag сильным автоматически.

## Когда применять

Для ресурсов с риском lost update. Выберите один контракт: ETag/If-Match с 412 либо поле revision с документированным 409. В профиле обязательного предусловия отсутствие If-Match дает 428; это выбранная политика проекта, а не требование всех HTTP API. If-Match: * проверяет существование, но не защищает от перезаписи другой версии, поэтому не заменяет конкретный ETag в таком профиле.

RFC допускает 2xx при уже примененном изменении; используйте это исключение только при доказуемом совпадении операции. Нельзя автоматически подставлять свежую версию и повторять чужую правку: нужен merge, повторное подтверждение или явно выбранная политика конфликтов.

## Как проверить

1. Два клиента получили один ETag → одновременные разные изменения → одно сохраняется, второе получает 412 → два ответа и одна новая версия БД.

2. Ресурс требует предусловия → запрос без If-Match или со слабым/устаревшим ETag → 428 для отсутствия, 412 для несовпадения, без записи → трасса и неизменное содержимое.

3. Первый ответ потерян → повтор той же операции → 412 с последующим чтением либо доказуемый 2xx без нового эффекта → журнал операции и отсутствие второй мутации.

## Человек

Определяет, какие ресурсы требуют защиты версии, и поведение интерфейса при конфликте.

## Агент

Реализует атомарную проверку версии, сильный ETag и согласованный контракт отсутствующего предусловия; воспроизводит гонку двумя запросами.
