# HTTP-методы

## Коротко

Выбирайте HTTP-метод по запрашиваемому эффекту. GET и HEAD не должны выполнять запрошенное клиентом изменение бизнес-состояния.

## Плохо

```http
GET /orders/42/delete HTTP/1.1
Host: api.example.com
```

## Хорошо

```http
DELETE /orders/42 HTTP/1.1
Host: api.example.com
```

## Почему

RFC 9110 различает безопасный метод и идемпотентный эффект. GET/HEAD допускают служебное журналирование; это не разрешает оплату или удаление по ссылке. Идемпотентность означает одинаковый целевой эффект повторов, а не одинаковые тело ответа и HTTP status code.

## Когда применять

Для HTTP API. POST обрабатывает команду или создает ресурс; PUT заменяет состояние целевого ресурса по контракту; DELETE удаляет связь ресурса с текущим представлением. PUT, DELETE и безопасные методы идемпотентны по семантике RFC. PATCH применяет изменение, которое само по себе не обязано быть идемпотентным: задайте формат, атомарность и условия повтора; для изменения от известной версии используйте предусловие. Ответ HEAD не содержит тела, но описывает представление по правилам HTTP.

Повтор DELETE может вернуть 204 после первого удаления и 404 после следующего; это не нарушение идемпотентности. Для существующего API смена метода требует миграции клиентов.

## Как проверить

1. Существующий заказ → GET/HEAD и предварительная загрузка ссылки → заказ не меняется, у HEAD нет тела → сравнение записи и HTTP-трассы.

2. Существующий заказ → два DELETE → ресурс остается удаленным, повтор не создает побочного бизнес-эффекта → состояние БД и журнал операций.

3. PATCH увеличения количества → потеря ответа → автоматический повтор допускается только при контракте дедупликации/предусловия → количество не увеличено непреднамеренно дважды.

## Человек

Определяет эффект команды, повторяемость и совместимость уже опубликованных методов.

## Агент

Сопоставляет маршруты с HTTP-семантикой; проверяет GET/HEAD и повтор записи отдельно от равенства ответов.
