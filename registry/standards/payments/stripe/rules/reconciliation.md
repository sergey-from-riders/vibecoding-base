# Платежная сверка

## Коротко

Сверяйте локальные платежи и возвраты с Stripe по устойчивому расписанию и checkpoint. Выборка только pending не обнаруживает поздний refund/dispute.

## Плохо

```text
Раз в час: найти order.status = pending; остальные платежи никогда
не сверять. Любой refund event означает полный возврат заказа.
```

## Хорошо

```text
Зафиксировать окно сверки и account/mode, читать все страницы.
Повторно проверить неопределенные платежи и изменения закрытых.
Сохранить результат страницы + checkpoint после успешного приема.
Сверить payment amount/currency, отдельные refund IDs/status/amount.
Безопасные переходы — идемпотентно; расхождение денег — на разбор.
```

## Почему

Webhook может быть пропущен, задвоен или обработан с задержкой; оператор может изменить платеж в Dashboard. PaymentIntent остается succeeded после refund/dispute. Поэтому сверка проверяет несколько связанных объектов и не заменяет их одним paid/refunded boolean.

## Когда применять

Для систем, где потеря платежного изменения влияет на товар, баланс, доступ или учет. Проект фиксирует период запуска, lookback/overlap, глубину повторной проверки, пагинацию, checkpoint, rate budget и максимальный возраст неразобранного расхождения. Не предполагайте наличие updated-фильтра у любого Stripe endpoint: выборка строится на документированных API, локальном реестре объектов и изменениях событий. Старые открытые refunds/disputes/неопределенные операции входят независимо от возраста создания.

Храните каждый refund по ID, сумме, валюте и статусу; несколько частичных возвратов не равны нескольким полным. Отдельно учитывайте succeeded, pending, failed/canceled/requires_action; не суммируйте все запросы как завершенные возвраты. Ограничьте новые возвраты доступной суммой с учетом уже завершенных и зарезервированных операций, используя идемпотентный запрос; Stripe также запрещает суммарный refund сверх исходной суммы. Учитывайте конкуренцию с Dashboard и dispute, при неизвестном результате сначала сверяйте, а не создавайте новый refund.

Автоматически допустимы только заранее описанные переходы с доказанной привязкой/суммой; повторная выдача не производится. Несовпадение account, валюты, суммы, двойное списание или конфликт возврата/спора получает владельца, причину, evidence IDs и срок разбора. Финансовую историю не переписывайте без следа: корректировка имеет источник и время.

## Как проверить

1. Webhook пропущен, затем два запуска сверки → чтение provider → локальное состояние восстановлено, выдача одна → checkpoint и business key.

2. Оплата 1000, возвраты 200 succeeded + 300 pending + 100 failed → сверка → завершено 200, pending 300, failed не вычтен → реестр по refund ID.

3. Сбой посередине страниц или поздний refund старой оплаты → повтор/overlap → нет потерянных объектов; денежное расхождение попало владельцу → метрика возраста и запись разбора.

## Человек

Задает окно/частоту, перечень допустимых автоисправлений и ответственного за финансовый разбор.

## Агент

Реализует checkpoint/повтор чтения, сверку отдельных refunds и идемпотентность исправлений без повторных выплат.
