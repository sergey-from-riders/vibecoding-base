# JSONB и реляционные поля

## Коротко

JSONB подходит для ограниченных документов со своей структурой. Стабильные ключи связей и авторизации моделируйте явно; JSON-синтаксис не проверяет бизнес-схему.

## Плохо

```sql
Весь заказ хранится в payload.
Доступ определяется payload.tenant, присланным клиентом.
Типы полей и размер документа не ограничены.
```

## Хорошо

```sql
CREATE TABLE orders (
  order_id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  total_minor bigint NOT NULL CHECK (total_minor >= 0),
  provider_snapshot jsonb NOT NULL
    CHECK (jsonb_typeof(provider_snapshot) = 'object')
);
-- tenant_id получает сервер; snapshot не источник авторизации.
```

## Почему

Пример показывает только границу реляционных полей и снимка; валюта и полная схема заказа описываются отдельно. CHECK object не заменяет валидацию вложенных полей. JSONB не сохраняет исходные байты, порядок ключей и дубли ключей; он не подходит для последующей проверки подписи исходного webhook.

## Когда применять

Для PostgreSQL 18, внешних снимков и разреженных настроек. Зафиксируйте структуру, обязательность/null, допустимые ключи, размер/вложенность и совместимость изменений. Версия документа нужна, если потребитель различает несколько несовместимых структур; не добавляйте schema_version без потребителя.

Укажите источник истины для каждой копии значения: provider_snapshot может хранить историческую сумму, но текущая сумма/tenant берутся из авторитетных колонок. Часто фильтруемое поле не обязано немедленно стать колонкой: сначала оцените expression/GIN-индекс; перенос нужен при устойчивом инварианте, FK, критичных запросах или независимых обновлениях. Любое изменение JSONB блокирует всю строку, поэтому огромный общий документ ухудшает конкуренцию. Перенос поля выполняйте совместимой миграцией.

## Как проверить

1. Валидный снимок в бюджете → запись → известная структура и авторитетные колонки согласованы → сохраненная запись и валидатор.

2. Массив вместо объекта, неверный тип/версия или превышение размера → вход → отказ до бизнес-эффекта → ошибка валидации/constraint.

3. Клиент подменяет tenant внутри JSON или обновляет независимое поле конкурентно → доступ не меняется, конфликт не теряет обновление → проверка прав и двух транзакций.

## Человек

Определяет владельца данных, устойчивые поля и действительно нужную версионность документа.

## Агент

Разделяет снимок и источник истины, валидирует структуру/бюджет и измеряет запросы до выбора индекса или колонки.
