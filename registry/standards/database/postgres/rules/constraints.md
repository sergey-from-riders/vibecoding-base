# Ограничения целостности

## Коротко

Закрепляйте устойчивые инварианты данных ограничениями БД, если они выразимы в выбранной СУБД. Предварительная проверка приложения помогает UX, но не заменяет конкурентно корректное ограничение.

## Плохо

```sql
-- Приложение отдельно проверило отсутствие email.
-- Два запроса одновременно вставили одинаковое значение.
CREATE TABLE users (tenant_id uuid, email_key text);
```

## Хорошо

```sql
CREATE TABLE users (
  user_id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  email_key text NOT NULL,
  CONSTRAINT users_tenant_email_unique UNIQUE (tenant_id, email_key)
);
```

## Почему

Пример PostgreSQL 18 закрепляет выбранную уникальность внутри tenant. email_key — результат согласованной канонизации, а не универсальное lower(email): правила регистра и подтверждения адреса определяет продукт. UNIQUE и NOT NULL решают разные задачи; по умолчанию несколько NULL не нарушают UNIQUE. CHECK также допускает NULL-результат, поэтому запрет отсутствия задается отдельно.

## Когда применять

Для реляционной записи из приложения, импорта и фоновых задач. Выберите NOT NULL для обязательного значения, CHECK для инварианта строки, UNIQUE/EXCLUDE для подходящего инварианта между строками, FK для ссылки. Не используйте CHECK с чтением других строк как замену корректному ограничению. Если NULL должен участвовать в уникальности как обычное значение, PostgreSQL 18 поддерживает NULLS NOT DISTINCT.

До миграции выявите существующие нарушения и согласуйте очистку. Обрабатывайте ошибки по SQLSTATE/имени известного ограничения: например, 23505 нужного бизнес-ключа превращается в документированный конфликт, а не любой 500 в «email занят». Ограничение tenant не является авторизацией.

## Как проверить

1. Две транзакции создают один (tenant_id, email_key) → commit → одна запись, второй конфликт 23505 → содержимое таблицы и ответ приложения.

2. Отсутствующий обязательный email_key → INSERT → отказ NOT NULL; другой tenant с тем же ключом → допустим → SQLSTATE и выборка.

3. Импорт обходит API → нарушает CHECK/FK/UNIQUE по модели → БД отвергает нарушение; легитимные значения проходят → журнал миграции и контрольные строки.

## Человек

Фиксирует бизнес-ключи, обязательность, нормализацию и правила очистки исторических данных.

## Агент

Подбирает декларативное ограничение и обработку конкретного конфликта; проверяет конкурентную запись и прямой импорт.
