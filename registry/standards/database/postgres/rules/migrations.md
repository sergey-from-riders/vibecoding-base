# Миграции схемы

## Коротко

Изменяйте production-схему с учетом одновременно работающих версий приложения, живых записей и ограничений DDL. Уже примененную миграцию не переписывайте.

## Плохо

```text
Удалить old_amount → развернуть новый код.
Заполнить new_amount один раз, пока старый код продолжает писать old_amount.
```

## Хорошо

```text
Expand: добавить совместимое поле.
Обеспечить согласованную запись старого и нового представления.
Backfill порциями с checkpoint, безопасный при повторе.
Сверить данные и переключить чтение.
После завершения поддержки старого кода — contract/удаление.
```

## Почему

Expand/contract уже нужен исходному правилу; важное уточнение — backfill не должен перезаписывать более новые записи. Выберите один контролируемый механизм синхронизации: совместимый код записи, временный триггер или окно остановки записи. Самостоятельные несогласованные dual writes в разные транзакции не обеспечивают инвариант.

## Когда применять

Для БД с данными и независимым выпуском приложений. В PostgreSQL 18 проверьте нужную блокировку каждой команды, допустимые lock_timeout/statement_timeout и объем WAL/реплик. Пределы выбираются по бюджету проекта. Не запускайте одну миграцию конкурентно несколькими экземплярами: нужен единственный исполнитель/координационная блокировка с явным завершением.

Backfill хранит прогресс, выполняется ограниченными транзакциями, учитывает текущую версию строки и возобновляется после сбоя. Валидируйте инвариант до обязательности/переключения. Для поддерживаемых CHECK/FK можно отдельно добавить NOT VALID и затем VALIDATE: это не разрешение оставить старые данные непроверенными навсегда. CONCURRENTLY и другие команды вне transaction block имеют отдельный план частичного сбоя. Для удаления данных определите восстановление из копии/forward fix; down не восстанавливает утраченное автоматически.

## Как проверить

1. Старый и новый код на расширенной схеме → записи во время backfill → обе версии читают согласованные значения → сравнение данных и контрактные запросы.

2. Мигратор не получил lock в бюджете → выполнение → предсказуемый отказ без бесконечного ожидания; второй мигратор не выполняет ту же работу → журнал координатора.

3. Сбой посередине backfill/нетранзакционного DDL → повтор → продолжение с checkpoint и проверка частичного результата → счетчики сверки/каталог схемы, без потери новой записи.
