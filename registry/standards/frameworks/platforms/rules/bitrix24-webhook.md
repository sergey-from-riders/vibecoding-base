# Bitrix24: серверный вебхук

## Коротко

Секрет входящего вебхука хранится на сервере и не попадает в браузер, URL собственного API или журналы. Собственный endpoint проверяет клиента и допускает только конкретную бизнес-операцию.

## Плохо

```text
Браузер вызывает https://portal.bitrix24.ru/rest/1/SECRET/crm.lead.add.
Серверный proxy принимает произвольные portal, method и поля от браузера.
При таймауте crm.lead.add повторяется с новым request_id.
```

## Хорошо

```text
Клиент -> POST /api/leads: аутентифицированный запрос, допустимые поля.
Сервер -> фиксированный portal и crm.lead.add; секрет из серверного хранилища.
Журнал: operation_id, portal_id, метод, безопасный код результата, без URL секрета.
Локальная операция создана атомарно с устойчивым ключом и состоянием pending.
Получен CRM ID -> сохранен результат; повтор возвращает тот же результат.
Таймаут -> состояние unknown и сверка; слепого нового создания нет.
```

## Почему

URL входящего вебхука содержит учетный секрет и дает возможности в пределах scope и прав его владельца. Перенос URL на сервер уменьшает раскрытие, но открытый универсальный proxy все равно позволяет постороннему действовать от имени интеграции.

## Когда применять

Входящий вебхук для выбранного Битрикс24. Это не правило проверки исходящего webhook-события и не замена OAuth установочного приложения. Выберите минимальные scope и подходящего владельца; подтвердите доступность нужного метода для вебхука.

В собственном API проверьте аутентификацию, право на операцию, CSRF при cookie-сессии, поля и ограничения нагрузки. Не разрешайте клиенту задавать домен, полный URL или произвольный REST-метод. Настройте редактирование URL в reverse proxy, HTTP-клиенте, APM, exception report и трассировке: маскировки одного query string недостаточно, секрет находится в path.

При утечке отзовите/замените вебхук, обновите серверный секрет и проверьте отказ старого. Учитывайте смену владельца, прав и срока действия; одинаковый URL не гарантирует неизменные полномочия.

`operation_id` и таблица соответствий CRM ID — ваш протокол, не универсальная идемпотентность Bitrix24. Создавайте запись операции атомарно с ограничением уникальности; после неизвестного результата сверяйте устойчивый внешний идентификатор в выбранной CRM-сущности. Обычный «найти, затем создать» без защиты гонки не исключает дубликаты. Если API не дает достаточной сверки, остановите автоматический повтор и оставьте состояние unknown для разбора.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Авторизованный клиент создает заявку | Создан разрешенный объект, CRM ID сохранен | Ответ API и запись операции |
| Гость, чужой объект или подмена REST-метода/portal | Отказ до вызова Bitrix24 | Отрицательный тест и счетчик внешних вызовов |
| Ошибка внешнего запроса | Секрета нет в bundle, сети браузера и всех слоях журналирования | Проверка артефактов и журналов |
| Два запроса с одним ключом; таймаут после создания | Один локальный владелец операции; сверка возвращает прежний CRM ID либо unknown | Конкурентный сценарий с управляемым таймаутом |
| Секрет отозван/заменен | Старый URL не работает; новый имеет только согласованные права | Проба без сохранения секрета в отчете |

Прохождение локального mock-теста не подтверждает реальные права, отзыв или свойства CRM API.

## Человек

Утверждает владельца вебхука, минимальные права и порядок разбора неизвестного результата.

## Агент

Прослеживает секрет во всех слоях и фиксирует ограничения дедупликации выбранного метода. Не создает универсальный REST proxy.
