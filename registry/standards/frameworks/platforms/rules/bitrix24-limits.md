# Bitrix24: лимиты и повтор запросов

## Коротко

Ограничивайте поток по порталу и учетному контексту, различайте лимиты частоты и времени метода, а результаты batch обрабатывайте по каждой команде. Повтор имеет срок и бюджет.

## Плохо

```text
while ошибка:
    немедленно повторить весь batch
HTTP 200 считается успехом всех команд.
После timeout все crm.*.add выполняются заново.
```

## Хорошо

```text
Очередь portal + приложение/вебхук -> ограниченное число запросов.
QUERY_LIMIT_EXCEEDED -> снижение частоты, backoff с jitter.
OPERATION_TIME_LIMIT -> пауза конкретного метода с учетом operating_reset_at.
batch.result.result -> записать успех по command_id.
batch.result.result_error -> классифицировать и повторить только допустимое.
Нет результата команды/таймаут -> сверить устойчивый внешний ID.
Исчерпан deadline/бюджет -> остановить повторы, сохранить причину и уведомить.
```

## Почему

Параллельные повторы усиливают перегрузку. Успешный HTTP-ответ batch не означает успех каждого REST-метода, а повтор целого пакета может повторно создать уже созданные объекты.

## Когда применять

REST Битрикс24. Пример структуры ответа относится к классическому `batch`, не переносится без проверки на batch REST 3.0. Лимиты облака зависят от тарифа/конфигурации; у коробки свои серверные ограничения. Не фиксируйте одно число запросов для всех установок.

По текущей документации `QUERY_LIMIT_EXCEEDED` связан с интенсивностью запросов, `OPERATION_TIME_LIMIT` — с накопленным временем конкретного метода в контексте приложения/вебхука. `operating_reset_at` помогает выбрать первую повторную попытку, но не обещает полного обнуления всех временных корзин. Ограничение очереди по порталу координирует ваши процессы, не отменяя нагрузку других интеграций.

Для batch учитывайте `halt`: при `halt=1` команды после ошибки могут не выполняться; отсутствие результата не равно успеху. Сохраняйте checkpoint каждой команды до подтверждения очереди. Для создания используйте устойчивый внешний ключ, связанный с исходной бизнес-операцией, и протокол сверки неизвестного результата; наличие своего request_id не добавляет поддержку идемпотентности удаленному методу.

До запуска задайте max attempts, deadline, максимальный возраст очереди и канал разбора окончательного отказа. Это параметры проекта с обоснованием, а не числа API. Ошибки прав/параметров не исправляются backoff; transient-ошибку повторяют только если операция безопасна к повтору.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Имитация QUERY_LIMIT_EXCEEDED в нескольких worker | Общая частота уменьшается, задержки не синхронны | Метрики частоты, backlog и времени повторов |
| OPERATION_TIME_LIMIT для одного метода | Этот метод приостановлен до допустимой попытки; нет обхода лимита новыми worker | Записанные operating/reset_at и расписание |
| Batch: успех A, ошибка B, C не выполнен при halt=1 | A не повторяется, B классифицирован, C остается неподтвержденным | Состояния команд после перезапуска |
| Таймаут создания и перезапуск процесса | Восстановлен прежний ключ; сверка или unknown, не новый объект вслепую | CRM и durable checkpoint |
| Бюджет или срок исчерпан | Повторы остановлены, причина доступна ответственному | Финальное состояние и уведомление |

Проверяйте вложенный REST-результат вместе с HTTP-статусом и метриками, без записи секретного URL.
