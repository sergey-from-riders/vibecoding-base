# Laravel: Eloquent и N+1

## Коротко

Для ограниченной страницы загружайте используемые связи заранее, применяйте фильтр доступа до пагинации и измеряйте запросы всего формирования ответа, включая ресурс или шаблон.

## Плохо

```php
foreach (Order::all() as $order) {
    echo $order->customer->name; // Неограниченная выборка и N+1.
}
```

## Хорошо

```php
use App\Models\Order;

// tenantId получен из доверенного контекста пользователя.
$orders = Order::query()
    ->where('tenant_id', $tenantId)
    ->with('customer')
    ->orderBy('id')
    ->paginate(30);

foreach ($orders as $order) {
    echo e($order->customer?->name ?? 'Клиент не указан');
}
```

## Почему

Ленивая загрузка связи в цикле добавляет запросы с ростом количества строк. Eager loading ограничивает этот рост для заданных связей. Пагинация ограничивает размер страницы, но сама по себе не устраняет запросы из сериализатора.

## Когда применять

Laravel 12.x. У `Order` есть обычная `belongsTo`-связь `customer`; null допустим в этом примере. Если связь обязательна, обеспечьте это схемой и не скрывайте повреждение данных заглушкой. Выборка customers также должна соответствовать модели доступа: глобальная уникальность ID не заменяет целостность tenant-связей.

30 — размер страницы примера, а не универсальный лимит. Для простой связи обычно нужны запросы count, заказов и клиентов; scope, middleware, вложенные и полиморфные связи меняют число. Зафиксируйте бюджет для конкретного endpoint и набора данных. `simplePaginate` убирает count, если общее число не требуется; большой экспорт требует отдельного batch/streaming-сценария.

Не загружайте все возможные связи «на всякий случай». Если ответ обращается к `customer.address` или accessor делает запрос, включите это в план и измерение. `Model::preventLazyLoading(...)` в среде разработки помогает обнаружить часть нарушений; он не заменяет профиль запросов.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Ответы для 1 и 30 заказов с клиентами | Запросы обычной customer-связи не растут на один для каждой строки; бюджет учитывает count | SQL trace всего HTTP-ответа |
| Ресурс дополнен вложенной связью | Нет новых повторяющихся SELECT на каждую строку | Trace после сериализации |
| Заказ без customer | Согласованная заглушка без исключения; либо отказ при нарушении обязательной схемы | Ответ и fixture |
| Пользователь tenant A запрашивает список с данными A и B | Нет заказов и закрытых полей клиентов B | Интеграционный тест двух tenants |

Для измерения отключите отладочные запросы либо явно включите их в отдельную часть бюджета; фиксируйте размер fixtures и использованную БД.

## Человек

Выбирает размер страницы, перечень возвращаемых связей и бюджет SQL для пользовательского сценария.

## Агент

Показывает запросы после полной сериализации, проверяет nullable-связь и доступ. Не обещает всегда два запроса для любой схемы.
