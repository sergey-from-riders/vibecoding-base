# 1С-Битрикс: ключ кеша и инвалидация

## Коротко

Ключ кеша должен различать контексты, которые меняют ответ, а выдача должна учитывать текущие права. Канонизация фильтра, версия формата и инвалидация после commit входят в один контракт кеширования.

## Плохо

```php
$cacheId = 'orders_' . json_encode($_GET);
// Ответ пользователя A может быть выдан B, фильтр не нормализован.
```

## Хорошо

```php
// Все значения ниже получены из проверенного серверного контекста.
$filter = ['status' => $validatedStatus, 'page' => $validatedPage];
$cacheId = 'orders:v2:' . hash('sha256', json_encode([
    'tenant' => $tenantId,
    'user' => $userId,
    'permissions' => $permissionVersion,
    'site' => $siteId,
    'language' => $language,
    'filter' => $filter,
], JSON_THROW_ON_ERROR));
// Доступ проверяется до чтения кеша; version берется из актуального источника.
// При изменении данных очищается область orders данного tenant после commit.
```

## Почему

Неполный ключ смешивает ответы разных пользователей или фильтров. TTL лишь ограничивает давность; он не разрешает выдавать данные после отзыва доступа. Инвалидация до commit допускает заполнение старым значением между очисткой и фиксацией.

## Когда применять

Bitrix D7 Cache; фрагмент ключа требует PHP 7.3+ из-за `JSON_THROW_ON_ERROR`. `permissionVersion` — механизм приложения, а не встроенное поле Bitrix. Он полезен только при актуальном чтении и надежном изменении вместе с правами. Если такой версии нет, используйте другую проверенную схему разделения и очистки; не подставляйте фиктивную константу.

Нормализуйте типы, значения по умолчанию и порядок ключей/множеств фильтра до хеширования. Сайт, язык, валюта и tenant включаются, если влияют на результат; лишние измерения ухудшают hit rate. Префикс v2 меняется при несовместимом изменении структуры значения.

При `initCache` используйте сохраненное значение только после проверки доступа. При `startDataCache` завершайте успешный расчет через `endDataCache`; при исключении вызовите `abortDataCache` и не сохраняйте ошибку как валидный ответ.

Опишите область очистки после commit, допустимую давность и гонку повторного заполнения. Для строгой свежести нужна согласованная версия данных или иной протокол; одна очистка не исключает позднюю запись старого расчета. При высокой нагрузке предусмотрите ограничение параллельного пересчета; Cache API само по себе не обещает выбранную вами защиту от stampede.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| Эквивалентные фильтры с разным порядком входных полей | Один ключ и одинаковый ответ | Таблица нормализации |
| Разные tenant/user/язык, меняющие ответ | Разные ключи; нет чужих записей | HTTP-ответы и ключи без секретов |
| Отзыв права после заполнения кеша | Следующее чтение не раскрывает закрытые данные | Сценарий отзыва и ответа |
| Изменение записи с rollback; затем с commit | Rollback не публикует новые данные; commit инвалидирует нужную область | Журнал БД и кеша |
| Старый расчет заканчивается после инвалидации; расчет падает | Гонка укладывается в согласованную свежесть; ошибка не сохранена | Конкурентный сценарий и проверка abort |

Секреты и персональные значения в ключах и диагностике не нужны: хеш не заменяет управление доступом к кешу.

## Человек

Устанавливает допустимую давность и последствия отзыва права, определяет необходимые измерения ключа.

## Агент

Показывает источник каждой версии, область очистки и ошибочный путь расчета. Не принимает TTL за проверку полномочий.
