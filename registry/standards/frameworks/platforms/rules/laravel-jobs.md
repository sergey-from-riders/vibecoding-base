# Laravel: транзакция и afterCommit

## Коротко

Если задание зависит от записи внутри транзакции, отправляйте его после успешного внешнего commit. Отдельно решайте потерю задания между commit и отправкой, а также повторный внешний эффект.

## Плохо

```php
// Для соединения очереди after_commit=false.
DB::transaction(function () {
    $order = Order::create(['status' => 'new']);
    SendReceipt::dispatch($order->id); // Worker может опередить commit.
});
```

## Хорошо

```php
use App\Jobs\SendReceipt;
use App\Models\Order;
use Illuminate\Support\Facades\DB;

DB::transaction(function () {
    $order = Order::create(['status' => 'new']);
    SendReceipt::dispatch($order->id)->afterCommit();
});
```

## Почему

Отложенная отправка не дает worker прочитать еще не зафиксированную запись и отменяется при rollback. Но фиксация БД и передача сообщения брокеру остаются разными действиями: процесс может завершиться между ними.

## Когда применять

Laravel 12.x, обычная асинхронная очередь и `SendReceipt` с `ShouldQueue` и штатными traits для dispatch. Модель и схема примера допускают создание заказа с status. Запуск через sync-драйвер не доказывает поведение отдельного worker.

При `after_commit=true` на соединении очереди обычный `dispatch` уже ожидает завершения открытых родительских транзакций; повторять настройку на каждом вызове не обязательно. `afterCommit()` задает нужное поведение локально при `after_commit=false`. Если транзакции нет, ожидать нечего.

Для гарантированного намерения отправки пишите outbox в одной транзакции с заказом. Идентификатор бизнес-операции, сохраненный результат отправки и протокол провайдера определяют обработку повторов. `ShouldBeUnique` ограничивает постановку/выполнение, но не делает письмо или платеж однократным: сбой после внешней отправки и до локальной отметки оставляет неопределенный результат.

## Как проверить

| Вход и действие | Ожидаемый результат | Свидетельство |
| --- | --- | --- |
| after_commit=false, dispatch с afterCommit внутри вложенной транзакции | Сообщения нет до внешнего commit; после него worker видит заказ | Отдельные соединения БД/очереди, журнал событий |
| Ошибка после dispatch и rollback | Нет зафиксированного заказа и сообщения от этой транзакции | Запрос БД и проверка очереди |
| after_commit=true, обычный dispatch | Те же границы commit без обязательного afterCommit на вызове | Проверка обеих конфигураций |
| Сбой процесса после commit, до публикации сообщения | Для обязательной доставки outbox остается и доставляется повторным проходом | Зафиксированная outbox-запись и доставка |
| Worker повторен после таймаута внешней отправки | Сверка по ключу провайдера или явный статус «результат неизвестен»; нет слепого нового эффекта | Ответ провайдера и журнал операции |

Queue fake полезен для проверки намерения dispatch, но сам по себе не подтверждает гонку с реальным worker или устойчивость outbox.

## Человек
