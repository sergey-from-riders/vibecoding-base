## Идентификаторы: UUID и bigint

### Коротко

UUID удобен для независимого создания записей и публичных идентификаторов. Имя поля и его тип — разные решения.

### Плохо

```sql
CREATE TABLE orders (
  order_id bigint PRIMARY KEY
);
-- Два независимых сервиса выдали order_id = 42.
```

### Хорошо

```sql
CREATE TABLE orders (
  order_id uuid PRIMARY KEY DEFAULT uuidv7()
);
-- PostgreSQL 18: генерация без общего счётчика.
```

### Почему

UUID уменьшает зависимость от единого генератора. Он не заменяет проверку доступа; UUIDv7 раскрывает временную составляющую.

### Когда применять

Числовой identity допустим в централизованной БД. UUIDv7 есть в PostgreSQL 18; UUIDv4 через gen_random_uuid() подходит там, где v7 недоступен.

### Как проверить

- Где создаётся идентификатор? Нужен ли единый счётчик? Проверяется ли доступ независимо от UUID?

### Агент

## Имена таблиц и полей

### Коротко

Из имени поля должно быть понятно, какую связь оно хранит.

### Плохо

```sql
CREATE TABLE sessions (
  id uuid, ref uuid
);
```

### Хорошо

```sql
CREATE TABLE sessions (
  session_id uuid PRIMARY KEY,
  user_id uuid REFERENCES users(user_id)
);
```

### Почему

Явные имена помогают читать запросы с несколькими таблицами.

### Когда применять

snake_case и entity_id — соглашение этого справочника. Название id допустимо в другом последовательном соглашении; массовое переименование существующей БД не требуется.

### Как проверить

- Можно ли без комментария понять назначение ref?

## Ограничения целостности

### Коротко

Проверка в приложении не защищает от конкурирующих запросов и другого клиента БД.

### Плохо

```javascript
if (!emailExists(email)) {
  insertUser(email);
}
```

### Хорошо


### Почему

## Внешние ключи

### Коротко

Внешний ключ не позволяет хранить ссылку на несуществующую запись.

### Плохо

```sql
user_id uuid -- связь известна только коду
```

### Хорошо

```sql
user_id uuid REFERENCES users(user_id)
  ON DELETE RESTRICT
```

### Почему

Без ограничения легко получить осиротевшие данные.

### Когда применять

CASCADE подходит только для действительно зависимых записей. В распределённом хранилище без FK нужен документированный контроль целостности.

## Дата и время: timestamptz

### Коротко

Момент времени и местное расписание — разные данные. PostgreSQL `timestamptz` хранит момент, но не исходное название часового пояса.

### Плохо

```sql
CREATE TABLE meeting (starts_at text);
-- '09.11.2026 10:00' без формата и часового пояса
```

### Хорошо

```sql
CREATE TABLE meeting (
  starts_at timestamptz NOT NULL,
  time_zone text NOT NULL
);
-- '2026-11-09T10:00:00+03:00', 'Europe/Moscow'
```

### Почему

Без зоны одна строка может означать разные моменты. Для будущего повторяющегося расписания нужен местный час и название зоны, а не только одна UTC-метка.

### Когда применять

PostgreSQL 18: `timestamptz` — события и аудит; `date` — календарная дата; `timestamp without time zone` вместе с зоной и правилом повтора — локальное расписание. Не добавляйте зону к дате рождения. Денежные типы вынесены в отдельное правило `database.money`.

### Как проверить

- Проверены преобразования UTC, разные зоны и переходы летнего времени?
- Различаются дата, момент и повторяющееся расписание?

### Человек

Определяет, хранится ли точный момент, местная дата или повторяющееся расписание.

### Агент

Выбирает типы по согласованной семантике, проверяет преобразования зон и неоднозначное местное время.

## История и удаление данных

### Коротко

Мягкое удаление, история версий и аудит решают разные задачи.

### Плохо

```text
deleted_at есть, но все запросы читают удалённое.
```

### Хорошо

```text
Чтение учитывает deleted_at.
Уникальность и восстановление проверены.
Срок окончательной очистки определён.
```

### Почему

Флаг удаления сам по себе не удаляет данные и не создаёт историю изменений.

### Когда применять

Аудит фиксирует, кто и что изменил; история версий позволяет восстановить прежнее содержимое. Выберите нужные механизмы отдельно. При soft delete проверьте уникальность активных записей, восстановление и окончательную очистку. Срок хранения задаёт политика проекта.

## Деньги: bigint, numeric и валюта

### Коротко

Сумма хранится вместе с валютой и единицей измерения. Для расчётов используйте целые минимальные единицы или точный десятичный тип.

### Плохо

```sql
CREATE TABLE price (amount double precision);
-- 123.45: неизвестны валюта и политика округления
```

### Хорошо

```sql
CREATE TABLE price (
  amount_minor bigint NOT NULL CHECK (amount_minor >= 0),
  currency text NOT NULL CHECK (currency = 'RUB')
);
INSERT INTO price VALUES (12345, 'RUB'); -- 123 руб. 45 коп.
```

### Почему

`float`, `real` и `double precision` не гарантируют точное представление десятичных денежных дробей. Проверка в БД удерживает формат даже при записи другим сервисом.

### Когда применять

PostgreSQL 18. Тип выбирается по единице измерения и максимальной сумме:

- `integer` / `int`: целые минимальные единицы в доказанном диапазоне. Максимум 2 147 483 647, то есть 21 474 836,47 RUB при хранении копеек.
- `bigint`: целые минимальные единицы, если диапазона `integer` недостаточно. У него тоже есть предел; это не бесконечный тип.
- `numeric(p,s)` / `decimal(p,s)`: точные десятичные суммы, дробные тарифы и курсы. `numeric(20,6)` допускает 14 целых и 6 дробных разрядов. Точность и округление задаёт предметная область.

В примере поддерживается только RUB. Для нескольких валют нужна проверяемая таблица валют и их разрядности: не у всех валют две цифры после запятой; API провайдера может иметь исключения. Отрицательные суммы разрешайте для проводок, если это требует модель. PostgreSQL `money` зависит от денежных настроек локали, поэтому для переносимого контракта предпочтительнее явно заданные единицы.

В JavaScript `Number` гарантирует точность целых только в безопасном диапазоне от −(2^53 − 1) до 2^53 − 1. Большие `bigint` передавайте в JSON строкой; преобразование и арифметику выполняйте без промежуточного `float`.

### Человек

Определяет валюты, максимальные суммы, точность тарифов и правила округления/возвратов.

### Агент

Готовит поля БД, ограничения и сериализацию. Проверяет точность на граничных суммах и сверяет единицы платёжного API.

### Пример применения

Магазин принимает RUB: цена 1999,90 ₽ хранится как `199990` в `amount_minor bigint`. Комиссия рассчитывается десятичной арифметикой, округляется по согласованному правилу до копеек и только затем сохраняется. Для бухгалтерских проводок создаётся отдельная модель с допустимым отрицательным знаком.

### Как проверить

- 12345 минимальных единиц RUB преобразуются в 123,45 ₽ и обратно без потери копеек.
- Проверены предел типа, отрицательные значения, дробное деление и округление.
- В API описаны валюта, единица и строковый формат больших целых.
