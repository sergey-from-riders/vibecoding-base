# Контракт контента для публикации

Канонический источник — `rules/*.md`. Формат ниже сверён с `tools/standards-content.mjs` и совпадающим парсером eval.su 13 ноября 2026 года. Генератор, профили и проверки остаются в этом репозитории; сайт не исполняет код из загружаемого Git-снимка.

## 1. Источники и снимок

Потребитель сначала разрешает выбранный ref в полный commit SHA, затем читает все данные только из этого commit. Обращение к меняющемуся `main` для каждого файла отдельно не создает согласованного снимка.

| Набор | Путь | Содержимое |
| --- | --- | --- |
| Разделы | `registry/handbook/<id>.md` | Frontmatter раздела и короткое описание |
| Правила | `registry/standards/<domain>/<module>/rules/<slug>.md` | Frontmatter правила и фиксированные смысловые блоки |
| Иллюстрации | `registry/standards/<domain>/<module>/assets/<name>.webp` | Изображения, на которые ссылаются правила |

`standard.md`, CHANGELOG, README, профили, аудиты и промпты не являются правилами публикационной коллекции. Нельзя включать их простым обходом всех `.md` в репозитории. Путь — относительный от корня, с прямыми слешами; обход родительских каталогов и загрузка файлов за пределами снимка запрещены.

Для исходного снимка `613500afd8eca5143b4094f6f5cd48e67844f8ff` ожидаются 142 правила, 16 разделов и 6 WebP. Это контрольная база, а не постоянный лимит для будущего роста.

## 2. Frontmatter версии 1

Документ — UTF-8 без BOM. Начало и конец frontmatter обозначаются отдельными строками `---`. Каждая строка между ними имеет вид `key: JSON-value`: имя состоит из строчных латинских букв и подчеркивания, после двоеточия один пробел. Ключ не повторяется. Каждое значение должно самостоятельно разбираться как JSON.

Корректные примеры значений:

```text
schema_version: 1
id: "backend.context"
tags: ["go", "отмена"]
sources: ["https://go.dev/doc/database/cancel-operations"]
```

Это ограниченное подмножество YAML, а не произвольный YAML-документ. Комментарии, YAML-якоря, теги, даты без кавычек, многострочные значения и неявные типы не применяются. CRLF нормализуется в LF. Размер исходного документа не превышает 100 000 байт; блок метаданных короче 16 000 символов.

### Поля правила

| Поле | Обязательность | Тип и ограничение |
| --- | --- | --- |
| `schema_version` | Да | Число `1` |
| `id` | Да | Строка `<section>.<slug>`; обе части соответствуют `[a-z][a-z0-9-]{0,79}` |
| `title` | Да | Непустая строка до 160 символов |
| `section` | Да | ID существующего раздела; совпадает с первой частью `id` |
| `level` | Да | `required`, `recommended` или `contextual` |
| `tags` | Да | Массив до 30 непустых строк, каждая до 200 символов; может быть пустым |
| `technologies` | Да | Такой же массив названий технологий |
| `published_at` | Для новых публикаций | Подтвержденная календарная дата `YYYY-MM-DD`; старые документы без нее читаются без выдуманной подстановки |
| `reviewed_at` | Да | Календарная дата последнего содержательного ревью `YYYY-MM-DD` |
| `order` | Да | Положительное целое число; при одинаковом order порядок определяется ID |
| `related` | Да | Массив до 30 ID существующих других правил; самоссылки запрещены |
| `sources` | Да | От 1 до 30 уникальных HTTPS URL, до 200 символов каждый, без логина и пароля |
| `illustrations` | Нет | Объект ровно с ключами `bad` и `good`; формат ниже |

Не расширяйте список полей и допустимых значений несогласованно. Парсер схемы 1 игнорирует неизвестные поля; это не является обязательством потребителя поддерживать новый смысл. Изменения контракта рассматриваются отдельно от правок текста.

### Поля раздела

| Поле | Обязательность | Тип и ограничение |
| --- | --- | --- |
| `schema_version` | Да | Число `1` |
| `id` | Да | `[a-z][a-z0-9-]{0,79}`; совпадает с именем файла |
| `title` | Да | Непустая строка до 100 символов |
| `order` | Да | Положительное целое число |
| `parent` | Нет | ID другого раздела без собственного родителя; один уровень вложенности |

После метаданных идет непустое описание раздела до 1000 символов. В коллекции не должно быть пустых разделов, повторных ID, отсутствующего родителя или цикла вложенности.

## 3. ID, пути и связи

Путь правила имеет вид `registry/standards/<domain>/<module>/rules/<slug>.md`. Части каталогов и имя файла состоят из строчных латинских букв, цифр и дефисов. Последняя часть `id` совпадает с именем файла без `.md`. Домен каталога не обязан совпадать с разделом навигации: это разные способы группировки.

ID правила уникален во всем корпусе. Опубликованные ID и пути сохраняются. Переименование или перенос требуют плана миграции ссылок и адресов у потребителя; старый ID не присваивается другому смыслу.

Каждый `related` разрешается внутри того же снимка. Потребитель проверяет это после чтения всей коллекции. Отсутствующее правило является ошибкой кандидата публикации, а не поводом молча удалить связь.

Валидатор ограничивает коллекцию 1–50 разделами и 1–2000 правилами. Для согласованного роста за эти пределы потребителю нужно явно изменить свои ограничения и проверить ресурсные бюджеты.

## 4. Заголовки и смысловые блоки

Первый заголовок тела — `# ` и точное значение `title`. До первого блока допускаются только пустые строки. Все блоки второго уровня имеют фиксированные имена и встречаются не более одного раза.

| Статус | Заголовок | Назначение |
| --- | --- | --- |
| Обязательно | `## Коротко` | Суть требования |
| Обязательно | `## Плохо` | Один ограниченный пример дефекта |
| Обязательно | `## Хорошо` | Один сопоставимый пример корректного поведения |
| Обязательно | `## Почему` | Причина и последствия |
| Обязательно | `## Когда применять` | Условия, ограничения и исключения |
| Обязательно | `## Как проверить` | Наблюдаемая приемка и свидетельство |
| Обязательно | `## Источники` | Точные первичные ссылки |
| Необязательно | `## Человек` | Решения и ответственность человека |
| Необязательно | `## Агент` | Действия и проверка в полномочиях агента |
| Необязательно | `## Пример применения` | Прикладной контекст и ограничения |

Каждый присутствующий блок непустой. Текущие материалы обычно используют 9 блоков, а с прикладным примером — 10. Обратная совместимость схемы 1 сохраняет 7 обязательных и до 3 необязательных блоков.

Для новых смыслов используйте `###` внутри существующих блоков: критерий приемки и свидетельство — внутри «Как проверить», ограничения и исключения — внутри «Когда применять». Новые заголовки `##` несовместимы с действующей схемой.

«Плохо» и «Хорошо» состоят каждый строго из одного fenced code block с тремя обратными кавычками. Тело примера — до 12 000 символов; язык — строчные латинские буквы, цифры, `+` или `-`, либо `text`. Отдельный поясняющий абзац или подзаголовок внутри этих двух блоков не допускается; пояснение размещается в других блоках. Все fenced blocks закрыты.

## 5. Источники и даты

Раздел «Источники» содержит обычные Markdown-ссылки вида `[название](https://...)`. URL совпадают с `sources` точно, включая фрагменты и параметры: одинаковое количество, ни одного пропуска, повтора или лишнего адреса. Веб-проверка ссылки отдельно от формата должна оценивать, подтверждает ли источник утверждение и соответствуют ли версии.

Даты проверяются как реальные календарные даты, без будущих значений на дату проверки; парсер сравнивает календарный день UTC. `published_at` не заменяется временем импорта, редактирования или ревью. `reviewed_at` обновляется только после проверки смысла. Неизвестная дата остается неизвестной.

Дату изменения файла потребитель получает из истории того же commit Git. Если история недоступна, нельзя выдавать день импорта за дату изменения. Используйте явно неизвестное значение в производном представлении либо остановите создание представления, если его контракт требует точную дату.

## 6. Иллюстрации

В `illustrations` обязательны обе стороны `bad` и `good`. Каждая содержит `path` и непустой `alt` до 500 символов. `path` начинается с `registry/standards/<domain>/<module>/assets/` того же модуля и содержит только безопасное имя файла из строчных латинских букв, цифр и дефисов.

Схема 1 разрешает PNG и WebP; существующие шесть иллюстраций сохранены в WebP. Для нового изображения проверяются существование в снимке, расширение, фактическая сигнатура формата и размер не более 500 000 байт. Путь не является внешним URL. В текущем снимке сохранены 6 существующих WebP.

Изображение дополняет текст. Понятность правила без изображения и корректный alt обязательны для приемки материала. Реальные секреты и данные пользователей в иллюстрациях не допускаются.

## 7. Проверка и безопасная публикация

Потребитель должен выполнять следующую последовательность:

1. Зафиксировать commit и получить полный ожидаемый набор файлов; проверить допустимые пути, размеры и кодировку.
2. Проверить все документы, а затем целостность коллекции: уникальность ID, разделы, related, источники, даты и изображения.
3. Построить кандидат страниц, поиска и экспорта из одного набора. Не смешивать их с предыдущей редакцией.
4. Проверить безопасный рендеринг Markdown, ссылки, примеры и иллюстрации; не исполнять код или команды из контента.
5. Опубликовать весь кандидат одной принятой ревизией. Сохранить исходный commit и версию преобразователя.

Ошибка загрузки, отсутствие файла, неизвестная схема, неверное поле или нарушенная связь останавливают приемку нового снимка. Это поведение fail-closed относится к смене публикации: посетители продолжают получать последнюю успешно принятую редакцию, last-known-good. Не допускаются частичная публикация и замена всего каталога пустым массивом при ошибке.

Сбой виден владельцу потребителя: какой commit проверялся, этап отказа и безопасное описание причины. Секреты и полные пользовательские данные не попадают в журнал.

## 8. Ревизия экспорта

Сайт использует полный commit SHA как `revision`. Страница и экспорт с этой ревизией читают один сохранённый снимок; экспорт указывает исходный commit, даты и первоисточники. Ревизия экспорта не подменяется датой ревью или временем запроса.

Текущий потребитель хранит текущую и предыдущую исправные версии. Если запрошенная версия уже недоступна, он сообщает об этом, а не выдаёт другую версию под прежним идентификатором.

Отдельный идентификатор версии преобразователя из входящего предложения в транспортный API не добавлен. Такое расширение требует отдельного изменения и проверки потребителя; оно не является существующим полем схемы 1.
