# Как предложить изменение

Справочник открыт для предложений. Для чтения сайт не требует регистрации; для PR нужна учётная запись GitHub.

1. Нажмите «Предложить изменение» на странице правила или откройте его файл в `registry/standards/<domain>/<name>/rules/`.
2. Нажмите карандаш на GitHub. Если у вас нет права записи, GitHub предложит создать fork — вашу копию репозитория.
3. Исправьте объяснение или пример. Укажите первоисточник и проверяемые версии. Обновляйте `reviewed_at` только после содержательной проверки.
4. Создайте ветку и pull request в `main`. Объясните причину изменения и проверку.
5. Редактор проверит технический смысл и примеры. После слияния сайт подхватит материал при очередной синхронизации.

Сам PR не публикует правило. Не присылайте секреты, реальные пользовательские данные и опасные исполняемые примеры.

## Формат правила

Один файл — одно правило. Frontmatter — ограниченный YAML: одна строка на ключ, значения записываются в JSON-синтаксисе (строки в двойных кавычках, массивы в квадратных скобках). Это делает формат одинаковым для сайта и проверки без исполнения кода.

Обязательные поля: `schema_version` (1), `id` (`section.slug`), `title`, `section`, `level` (`required`, `recommended`, `contextual`), `tags`, `technologies`, `reviewed_at` (`YYYY-MM-DD`), `order`, `related` (ID правил), `sources` (HTTPS-ссылки).

Обязательные разделы: «Коротко», «Плохо», «Хорошо», «Почему», «Когда применять», «Как проверить», «Источники». В «Плохо» и «Хорошо» — по одному fenced code block, включая `text` для обычных сценариев. Пример поясняет правило, а не представляет готовый код для production.

Основная категория одна; технологии, теги и связанные материалы обеспечивают дополнительные связи. Описания и порядок категорий хранятся в `registry/handbook/*.md`.

«Обязательно» действует в указанной области применения. Авторские соглашения нельзя выдавать за универсальный стандарт. Версия библиотеки — область проверки, а не обещание, что это последняя версия.

## Проверки перед слиянием

```bash
node tools/handbook.mjs generate
node tools/vibe.mjs use go-next-postgres --project examples/generated-go-next-postgres --force
node tools/vibe.mjs use python-react-postgres --project examples/generated-python-react-postgres --force
node --test tools/standards-content.test.mjs
node tools/vibe.mjs verify
```

Генератор обновляет `standard.md`. Проверка обнаруживает повторные ID, неверные даты, потерянные ссылки, пустые категории и расхождения с генерируемыми файлами. Она не подтверждает техническую корректность совета: это задача содержательного ревью. В этом репозитории не добавляется автоматический деплой из PR.

Для нового модуля добавьте `standard.yaml`, `README.md`, `CHANGELOG.md` и `rules/*.md`. Поля `standard.yaml` сохраняют прежний формат. `files.human_readable` указывает на генерируемый `standard.md`. Реальные проверки описываются в `checks.yaml`; не устанавливайте `enforcement.tested` без runtime-тестов.

Изменение смысла отражается в CHANGELOG и SemVer. Несовместимые правила требуют major-версии, корректировки диапазонов в профилях и регенерации примеров. Инструкции проекта и активные стандарты имеют приоритет над общими рекомендациями справочника в пределах поставленной задачи.

## Переход с версии 1

Версия 2 переносит исходный текст из `standard.md` в атомарные `rules/*.md` и делает русский основным языком. `standard.md` остаётся доступным для генератора. Идентификаторы существующих модулей сохранены, ссылки профилей обновлены до `^2.1.0`. Проекты с зафиксированной версией 1 не переписываются автоматически.

Исторические решения по всем исходным блокам находятся в [аудите](audit-2026-11-09.md). Новые изменения делаются в правилах, а не в этом историческом журнале.

## Роли и применение

У каждого правила должны быть `## Человек` и `## Агент`. Человек задаёт бизнес-ограничения и принимает значимые решения; агент исследует, реализует и проверяет работу в уже выданных полномочиях. Это не требует согласования каждого обратимого действия. Платформенные правила содержат `## Пример применения`, применимую версию и ограничения фрагмента кода. Заголовок — краткий технический термин.

Раздел может иметь `parent: "frontend"`; допускается один уровень вложенности. UI/UX сохраняет стабильные ID и адреса в `interface`, но отображается внутри Frontend.
