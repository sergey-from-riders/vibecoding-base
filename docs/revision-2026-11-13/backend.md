### api/openapi-modular

#### api.methods

[HTTP-методы](../../registry/standards/api/openapi-modular/rules/methods.md) · исходный аудит: 8/10, P2.

**Закрытие замечаний в тексте**

- Не разделены идемпотентный эффект и одинаковость ответов: повтор DELETE может менять код ответа → Разделены безопасный метод и идемпотентный эффект; служебное журналирование допустимо.
- Не обозначено, что безопасный метод допускает технические побочные эффекты вроде логирования, но не заказ или оплату → Уточнены HEAD, PUT, DELETE и возможность разных ответов на повтор.
- Проверка только открытия ссылки не покрывает HEAD и повторы PUT/DELETE → Добавлены приемка без изменения при GET/HEAD и проверка повторного PATCH.

**Проверенные первичные источники**

- [RFC 9110, §9.2–9.3: безопасность, идемпотентность, методы](https://www.rfc-editor.org/rfc/rfc9110.html#section-9).
- [RFC 5789, §2: семантика и атомарность PATCH](https://www.rfc-editor.org/rfc/rfc5789.html).

**Пример**

```http
DELETE /orders/42 HTTP/1.1
Host: api.example.com
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. Существующий заказ → GET/HEAD и предварительная загрузка ссылки → заказ не меняется, у HEAD нет тела → сравнение записи и HTTP-трассы.
2. Существующий заказ → два DELETE → ресурс остается удаленным, повтор не создает побочного бизнес-эффекта → состояние БД и журнал операций.
3. PATCH увеличения количества → потеря ответа → автоматический повтор допускается только при контракте дедупликации/предусловия → количество не увеличено непреднамеренно дважды.

#### api.concurrency

[Оптимистическая блокировка](../../registry/standards/api/openapi-modular/rules/concurrency.md) · исходный аудит: 7/10, P1.

**Закрытие замечаний в тексте**

- Проверка версии не названа атомарной с записью: отдельные SELECT и UPDATE оставляют окно гонки → Проверка и изменение атомарны; показана гонка отдельного SELECT и UPDATE.
- Не описано поведение при отсутствии обязательной версии и применимость сильного ETag → Определены сильный ETag, отсутствие предусловия, If-Match * и отдельный revision-контракт.
- Нет условия безопасного повтора после конфликта и запрета молчаливой перезаписи свежих данных → После конфликта предусмотрено чтение/merge, исключено слепое повторное перезаписывание.

**Проверенные первичные источники**

- [RFC 9110, §8.8.3 и §13.1.1: сильный ETag и If-Match](https://www.rfc-editor.org/rfc/rfc9110.html).
- [RFC 6585, §3: 428 Precondition Required](https://www.rfc-editor.org/rfc/rfc6585.html).

**Пример**

```text
GET /documents/42 → ETag: "v3"
А: PATCH с If-Match: "v3" → атомарная запись v4.
Б: PATCH с If-Match: "v3" → 412, запись не изменена.
Б получает v4 и предлагает пользователю сравнение изменений.
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. Два клиента получили один ETag → одновременные разные изменения → одно сохраняется, второе получает 412 → два ответа и одна новая версия БД.
2. Ресурс требует предусловия → запрос без If-Match или со слабым/устаревшим ETag → 428 для отсутствия, 412 для несовпадения, без записи → трасса и неизменное содержимое.
3. Первый ответ потерян → повтор той же операции → 412 с последующим чтением либо доказуемый 2xx без нового эффекта → журнал операции и отсутствие второй мутации.

#### api.headers

[HTTP-заголовки](../../registry/standards/api/openapi-modular/rules/headers.md) · исходный аудит: 6/10, P1.

**Закрытие замечаний в тексте**

- Название обещает общий стандарт заголовков, но содержание покрывает преимущественно код результата и Retry-After → Область сужена до базового профиля; Content-Type/Accept/Vary и связь с Cache-Control определены.

- Не сказано, когда Retry-After уместен, и какие заголовки должен видеть браузерный клиент через CORS → Собственные X-App-* не обязательны; проверяется потребитель перед удалением исторических заголовков.

**Проверенные первичные источники**

- [RFC 9110, §8.3, §10.2.3, §12.5: media type, Retry-After, negotiation](https://www.rfc-editor.org/rfc/rfc9110.html).
- [RFC 6585, §4: 429 и опциональный Retry-After](https://www.rfc-editor.org/rfc/rfc6585.html).
- [Fetch, CORS protocol: Access-Control-Expose-Headers](https://fetch.spec.whatwg.org/#http-access-control-expose-headers).

**Пример**

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/problem+json
Retry-After: 30

{"title":"Service Unavailable"}
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. JSON-ответ → обычный HTTP-клиент → распознает ошибку по status и тело по Content-Type → HTTP-трасса без зависимости от X-App-Result.
2. 503 с Retry-After и без него → клиент повтора → учитывает секунды/дату либо backoff в общем бюджете → временная шкала запросов.
3. Cross-origin браузер читает Retry-After → CORS-ответ → нужный заголовок доступен; локализованные кешируемые варианты разделены Vary → browser-тест и ответы прокси.

#### api.idempotency

[Идемпотентность API](../../registry/standards/api/openapi-modular/rules/idempotency.md) · исходный аудит: 8/10, P1.

**Закрытие замечаний в тексте**

- Не определены атомарное резервирование ключа, in-progress и конкурентный запрос с тем же ключом → Указаны атомарная резервация и поведение параллельного pending.
- Не описаны сбой после эффекта до сохранения результата и восстановление зависшей операции → Добавлены выбор сохраняемых ошибок и восстановление после внешнего эффекта.
- Не определено, какие ошибки и заголовки сохраняются для повтора; политика провайдера не всегда подходит своему API → Период ключа связан с повтором и проверкой истечения, без обещания exactly-once.

**Проверенные первичные источники**

- [RFC 9110, §9.2.2: идемпотентный эффект и повтор](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).
- [Stripe API: idempotent requests; отдельно v1/v2, TTL, pending](https://docs.stripe.com/api/idempotent_requests).

**Пример**

```text
Одна оплата: ключ K в области tenant + операция.
Атомарно резервируем K и fingerprint входа: pending.
Эффект и результат фиксируем вместе, если они в одной БД.
Повтор K с тем же входом получает прежний результат.
Внешний эффект: тот же ключ провайдера + сверка при сбое.
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. Два одновременных запроса с K и одинаковым входом → резервирование → один эффект, второй ожидает или получает документированный pending/результат → запись ключа и бизнес-объект.
2. K уже принят → иной payload либо другой пользователь → конфликт/отказ без раскрытия результата → HTTP-ответ и неизменные данные.
3. Провайдер применил команду, процесс упал до записи результата → повтор K и восстановление → один внешний эффект, локальный результат подтвержден сверкой → provider ID и журнал восстановления.
4. Ключ истек → повтор → поведение соответствует TTL-контракту; клиент не объявляет новую операцию безопасным retry → тест времени хранения.

**Ограничения.** Это синтаксический разбор и проверка формы минимального документа; официальный OAS validator, генерация SDK и фактический HTTP не запускались.

**Сценарии приемки для проекта**

[Подтверждение оплаты](../../registry/standards/payments/stripe/rules/payment-truth.md) · исходный аудит: 8/10, P1.

**Закрытие замечаний в тексте**

- Понятие конечного состояния не раскрывает различие authorization, processing, captured/succeeded и асинхронной оплаты → Разделены authorization, processing, capture/succeeded и отдельные критерии иных платежных профилей.
- Нет явного сопоставления платежа с merchant/account, окружением и владельцем локального заказа → Добавлена серверная привязка account/mode/order/owner с проверкой суммы и валюты.
- Не определена единая идемпотентная операция выдачи при одновременном webhook и серверной сверке → Webhook, redirect-triggered server read и reconciliation используют единый ключ исполнения.

**Проверенные первичные источники**

- [Stripe Payment status updates: PaymentIntent states и последующие Charge changes](https://docs.stripe.com/payments/payment-intents/verifying-status).
- [Stripe Checkout fulfillment: server function, concurrent calls, delayed payments](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page).

**Пример**

```text
Сервер: получить связанный PaymentIntent в нужном Stripe account/mode.
Сверить order, currency, ожидаемую и полученную сумму.
requires_action / processing / requires_capture → не считать оплатой.
succeeded → единая операция fulfill(order_id, payment_id).
Уникальный ключ выдачи + локальный эффект фиксируются атомарно.
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. Подтвержденный связанный succeeded с верной суммой → webhook одновременно с серверной сверкой → один эффект выдачи → UNIQUE/история операции.
2. Redirect paid=true, чужой payment_id либо неверные mode/account/currency/amount → проверка → выдачи нет → запись безопасного кода расхождения.
3. processing или requires_capture → сначала ожидание; затем succeeded → выдача один раз → последовательность состояний; последующий refund учитывается отдельно.

#### payments.reconciliation

**Закрытие замечаний в тексте**

- Нет модели частичных и нескольких возвратов, суммы уже возвращенного и несовпадения состояния → Возвраты моделируются по ID/status/amount; completed, pending и failed различаются.
- Не описано, какие расхождения исправляются автоматически, а какие требуют разбора и учета → Ограничены автоисправления; денежные конфликты имеют владельца, evidence и аудируемую корректировку.

- [Stripe Payment status updates: последующие изменения отражаются на Charge](https://docs.stripe.com/payments/payment-intents/verifying-status).
- [Stripe Webhooks: повторная доставка и отсутствие порядка](https://docs.stripe.com/webhooks).

**Пример**

```text
Зафиксировать окно сверки и account/mode, читать все страницы.
Повторно проверить неопределенные платежи и изменения закрытых.
Сохранить результат страницы + checkpoint после успешного приема.
Сверить payment amount/currency, отдельные refund IDs/status/amount.
Безопасные переходы — идемпотентно; расхождение денег — на разбор.
```

**Фактическая верификация.** Редакторская проверка семантики и сопоставимости пары; runtime-проверка приложения не выполнялась.

**Ограничения.** Сценарии приемки требуют реализации проекта-потребителя.

**Сценарии приемки для проекта**

1. Webhook пропущен, затем два запуска сверки → чтение provider → локальное состояние восстановлено, выдача одна → checkpoint и business key.
2. Оплата 1000, возвраты 200 succeeded + 300 pending + 100 failed → сверка → завершено 200, pending 300, failed не вычтен → реестр по refund ID.
3. Сбой посередине страниц или поздний refund старой оплаты → повтор/overlap → нет потерянных объектов; денежное расхождение попало владельцу → метрика возраста и запись разбора.

#### security.sql-injection

[SQL-параметры](../../registry/standards/security/no-secrets/rules/sql-injection.md) · исходный аудит: 9/10, P2.

**Закрытие замечаний в тексте**

- Проверка кавычек не задает ожидаемый результат: ввод должен оставаться данными, а не обязательно отклоняться → Кавычка остается допустимыми данными; acceptance задает буквальный поиск без расширения результата.
- Путь с разрешенным динамическим столбцом или направлением сортировки не проверен отдельным сценарием → Показан и проверяется отдельный allowlist динамического Identifier и неизвестный sort key.
- Версию dev-документации в подписи источника стоит уточнить относительно реально поддерживаемой версии драйвера → Источники уточнены до стабильной официальной документации Psycopg 3.3.9; runtime не заявлен.

**Проверенные первичные источники**

- [OWASP SQL Injection Prevention: binding, structural allowlist, least privilege](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).
- [Psycopg 3.3.9: Passing parameters to SQL queries](https://www.psycopg.org/psycopg3/docs/basic/params.html).
- [Psycopg 3.3.9: sql composition и Identifier](https://www.psycopg.org/psycopg3/docs/api/sql.html).

**Пример**

```python
from psycopg import sql


def find_users(cur, name, sort_key):
    columns = {"name": "name", "id": "id"}
    if sort_key not in columns:
        raise ValueError("unsupported sort key")
    query = sql.SQL(
        "SELECT id, name FROM users WHERE name = %s ORDER BY {} ASC"
    ).format(sql.Identifier(columns[sort_key]))
    cur.execute(query, (name,))
    return cur.fetchall()
```

**Фактическая верификация.** Python-блок разобран ast.parse; использование sql.Identifier и отдельных bound parameters сверено с Psycopg 3.3.9.

**Ограничения.** Psycopg/PostgreSQL runtime не выполнялся; parsing не доказывает отсутствие SQL injection в приложении.

**Сценарии приемки для проекта**

1. Имя O'Reilly → parameterized insert/read → сохранено и найдено без синтаксической ошибки → значение в тестовой БД.
2. Строка с кавычкой, OR и SQL-комментарием как name → запрос → ищется буквальное значение, набор строк не расширяется → контролируемые fixtures.
3. sort_key=name/id либо произвольный SQL-текст → запрос → разрешенный Identifier сортирует, неизвестный выбор отклоняется до execute → обе ветви allowlist.
