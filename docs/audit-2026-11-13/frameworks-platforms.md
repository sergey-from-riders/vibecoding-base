## laravel-jobs

**Laravel: транзакция и afterCommit** · `frameworks.laravel-jobs` · **9/10** · **P2**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/frameworks/platforms/rules/laravel-jobs.md) · [Текущий файл](../../registry/standards/frameworks/platforms/rules/laravel-jobs.md)

Применимость 2/2; Точность 2/2; Границы 2/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Учитывает after_commit в конфигурации, окно потери после commit и идемпотентность.

### Что уточнить

1. Не описана отдельная проверка after_commit=false и true
2. Не определено атомарное свидетельство выполненной отправки при повторе worker
3. Уникальный ключ задания не стоит приравнивать к гарантии однократного внешнего эффекта

### Сценарии приемки

1. Rollback при заданной конфигурации не публикует задание
2. После commit worker читает зафиксированный заказ
3. Сбой после фактической отправки и до подтверждения worker не создает повторного эффекта согласно выбранному контракту

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Открыта официальная документация Laravel 12.x Queues. Условия after_commit и afterCommit соответствуют тематике источника; сценарий exactly-once не следует выводить из одного queue API.

## bitrix-transactions

### Что сохранить

Проверяет Result и исключения, ограничивает атомарность одним соединением и БД.

1. Не раскрыты вложенные транзакции и поведение конкретного D7-соединения

3. Внутреннее событие вызывает внешний API: эффект явно не считается откатываемым вместе с БД

### Что сохранить

Корректно разделяет capability, nonce, проверенный ID, поля и ошибку wp_update_post.

### Что уточнить

1. Не названы минимальная версия WordPress и контекст admin-post/admin-ajax для примера
2. Нет проверки replay и срока nonce; нельзя трактовать nonce как одноразовый токен
3. Нужны согласованные статусы и поведение при несовпадении ID маршрута и тела

### Сценарии приемки

1. Разрешенная запись с правильным nonce меняет только title
2. Чужой ID не изменяется даже с nonce другой формы
3. Неверный/просроченный nonce отклоняется, а повтор допустимого запроса не считается автоматически заблокированным nonce

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Прочитан полный текст правила и указанные в нем ссылки. Внешние страницы для этого правила отдельно не перепроверялись; релевантность и актуальность требуют проверки при редактуре.
