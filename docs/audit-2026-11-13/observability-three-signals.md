## correlation

**Correlation ID** · `operations.correlation` · **8/10** · **P2**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/observability/three-signals/rules/correlation.md) · [Текущий файл](../../registry/standards/observability/three-signals/rules/correlation.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Разделяет request_id и trace_id, а входной идентификатор требует проверки размера и формата.

### Что уточнить

1. Не описано создание нового ID при отсутствии или недопустимом входном значении.
2. Нет границы доверия к trace context и связи с асинхронной задачей после завершения HTTP-запроса.
3. Проверка одного ID не учитывает sampling и срок хранения, поэтому полная трасса не всегда доступна.

### Сценарии приемки

1. Ответ и журнал одного запроса имеют согласованный безопасный request_id.
2. Слишком длинный или содержащий управляющие символы входной ID заменяется или отвергается без log injection.
3. Асинхронное задание сохраняет связь с исходной операцией; отсутствие sampled trace не приводит к обещанию полной трассы.

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

## http-spans

**HTTP spans** · `operations.http-spans` · **9/10** · **P2**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/observability/three-signals/rules/http-spans.md) · [Текущий файл](../../registry/standards/observability/three-signals/rules/http-spans.md)

Применимость 2/2; Точность 2/2; Границы 2/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Точное узкое правило правильно различает server/client для 404 и стандартный статус Unset для успешного HTTP.

### Что уточнить

1. Источник обновляется; нужны проверенная версия semconv и дата содержательной проверки.
2. Нужно явно отделить HTTP-код от ошибки при чтении тела и намеренной отмены клиентом.
3. Перечень тестов стоит превратить в таблицу HTTP-код/SpanKind/дополнительный контекст/ожидаемый статус.

### Сценарии приемки

1. Обычный HTTP 200 без иной ошибки дает Unset, а не принудительный OK.
2. Обычный 404 дает Unset на server span и Error на client span в отсутствие уточняющего контекста.
3. Сетевой сбой после заголовка 200 и намеренная отмена классифицируются по проверенной версии semconv, а не только коду ответа.

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Проверена текущая страница OpenTelemetry HTTP spans, раздел Status: [первоисточник](https://opentelemetry.io/docs/specs/semconv/http/http-spans/). Она содержит отдельные правила для сетевого сбоя и намеренной отмены; текущий основной пример статьи подтвержден.

## signals

**Observability** · `operations.signals` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/observability/three-signals/rules/signals.md) · [Текущий файл](../../registry/standards/observability/three-signals/rules/signals.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Выбирает сигналы по диагностической задаче и прямо запрещает неограниченную кардинальность user_id/полного URL.

### Что уточнить

1. Нет минимальной карты пользовательский сценарий → сигнал → способ обнаружения → действие.
2. Не определены пределы стоимости, sampling, хранения и действия при потере самой телеметрии.
3. Отсутствует проверка того, что отказ экспортера не блокирует основную обработку запросов.

### Сценарии приемки

1. Введенная ошибка обнаруживается выбранной метрикой и объясняется доступной диагностикой.
2. Скачок уникальных URL не создает неограниченное число рядов метрик.
3. Недоступный коллектор не останавливает сервис; потеря телеметрии становится наблюдаемой отдельным способом.

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

## slo

**SLO и error budget** · `operations.slo` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/observability/three-signals/rules/slo.md) · [Текущий файл](../../registry/standards/observability/three-signals/rules/slo.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Цель связана с успешным обслуживанием пользователя; произвольные 99.9% и 300ms не выдаются за универсальные нормы.

### Что уточнить

1. Не определены числитель, знаменатель, исключения и источник SLI: запросный показатель легко подменить инфраструктурным.
2. Нет точной модели окна, поведения при отсутствии трафика и объединении групп клиентов.
3. Error budget назван в заголовке, но его расчет и действия по скорости расходования не раскрыты.

### Сценарии приемки

1. Контрольный набор успешных и неуспешных запросов дает ожидаемое значение SLI по опубликованной формуле.
2. Окно без трафика и ошибки измерения не превращаются автоматически в 100% надежность.
3. Нарушение согласованного бюджета запускает назначенное действие с владельцем и критерием завершения.

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.
