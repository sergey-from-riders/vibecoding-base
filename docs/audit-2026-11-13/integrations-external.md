## timeouts

**Тайм-ауты интеграций** · `integrations.timeouts` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/integrations/external/rules/timeouts.md) · [Текущий файл](../../registry/standards/integrations/external/rules/timeouts.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 1/2.

### Что сохранить

Разделяет соединение и всю операцию и привязывает значения к измерениям.

### Что уточнить

1. Не включены DNS/TLS, чтение потока и бюджет нескольких попыток
2. Не описаны распространение дедлайна и отмена зависимых операций
3. Неопределенный результат записи после тайм-аута должен вести к ссылке на идемпотентность и сверку

### Сценарии приемки

1. Зависание соединения и медленное чтение завершаются в своих пределах
2. Несколько попыток вместе не превышают общего бюджета запроса
3. Тайм-аут записи не объявляет отсутствие эффекта без проверки фактического состояния

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

## retries

**Retry и backoff** · `integrations.retries` · **8/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/integrations/external/rules/retries.md) · [Текущий файл](../../registry/standards/integrations/external/rules/retries.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Задает ограничения попыток и времени, учитывает jitter и Retry-After.

### Что уточнить

1. Нет таблицы решений для идемпотентного чтения, записи и неопределенного результата
2. Не определены алгоритм backoff, предел задержки и общий дедлайн с учетом Retry-After
3. Не описано предотвращение перемножения повторов между несколькими слоями

### Сценарии приемки

1. 429 с Retry-After ожидается в пределах общего бюджета, без немедленного шторма
2. Постоянная ошибка валидации не повторяется
3. Тайм-аут после возможного применения записи приводит к сверке или безопасному повтору по тому же ключу

## oauth

**OAuth и PKCE** · `integrations.oauth` · **6/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/integrations/external/rules/oauth.md) · [Текущий файл](../../registry/standards/integrations/external/rules/oauth.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 1/2.

### Что сохранить

Выбирает Code + PKCE, минимальные scopes и запрет password grant.

### Что уточнить

1. Не разделены OAuth-доступ к API и OIDC-вход: issuer/nonce/ID token требуют своей области
2. Нет жизненного цикла одноразового state/verifier, S256, срока и проверки callback
3. Не уточнены public/confidential client, refresh-token rotation и защита токенов

### Сценарии приемки

1. Правильный code с привязанным verifier завершает начатую транзакцию
2. Подмена state/issuer/redirect и повтор кода не создают новую сессию
3. Токен другой аудитории и истекший токен не дают доступ к API

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Проверен RFC 9700, разделы 2.1.1 и 4.7.1: PKCE S256 и привязка к транзакции важны; варианты CSRF-защиты зависят от клиента. Требование state во всех потоках следует обозначать локальной усиленной политикой, а не буквальной общей нормой RFC. Ref: turn10view1, turn12view1.

## webhooks

**Подпись вебхуков** · `integrations.webhooks` · **8/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/integrations/external/rules/webhooks.md) · [Текущий файл](../../registry/standards/integrations/external/rules/webhooks.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Правильно требует исходные байты, подпись, срок и переносимость дубликатов.

### Что уточнить

1. Последовательность сохранить event_id затем обработать не задает атомарное состояние и может потерять событие после сбоя
2. Не определены подтверждение приема, быстрый ответ и возобновление незавершенной обработки
3. Общий стандарт с единственным Stripe-источником должен отделить provider-specific подпись, replay и ротацию

### Сценарии приемки

1. Измененные байты или неверная подпись отклонены до бизнес-эффекта
2. Дубликат корректного события не повторяет завершенный эффект
3. Процесс падает после устойчивого приема: событие остается pending и обрабатывается после восстановления

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

## mcp

**Авторизация MCP** · `integrations.mcp` · **4/10** · **P0**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/integrations/external/rules/mcp.md) · [Текущий файл](../../registry/standards/integrations/external/rules/mcp.md)

Применимость 1/2; Точность 0/2; Границы 1/2; Проверяемость 1/2; Примеры 1/2.

**Уже исправлено в этой ветке:** прямой запрет token passthrough, отдельный OAuth-токен для внешнего API, граница HTTP/STDIO и реалистичное окно отзыва. Сценарии ниже остаются частью приемки конкретной реализации. Балл 4/10 относится к исходнику, а не к новой редакции.

### Что сохранить

Правильно требует серверную проверку пользователя, scopes и объекта.

### Что уточнить

1. Фраза о передаче токенов после проверки аудитории ослабляет прямой запрет MCP token passthrough; upstream должен иметь отдельный токен
2. Не разделены HTTP authorization и STDIO: спецификация 2025-11-25 задает разные механизмы
3. Не описаны resource/audience binding, discovery и поведение при insufficient_scope
4. Проверка мгновенного отзыва требует выбранной модели introspection/expiry и не гарантируется любым JWT сама по себе

### Сценарии приемки

1. Токен, выданный другому resource, отклоняется до возврата данных
2. При обращении к upstream входящий MCP-токен не пересылается; применяется отдельная авторизация upstream
3. HTTP и STDIO проверяются по своим моделям, а срок применения отзыва соответствует документированному контракту

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Проверены MCP Authorization и Security Best Practices 2025-11-25: [первоисточник](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) . Token passthrough явно запрещен; разделы Purpose/Protocol Requirements отличают HTTP от STDIO. Ref: turn10view0, turn12view0.

Используйте вместе с общим промптом и исходным файлом.

иметь отдельный токен; Не разделены HTTP authorization и STDIO: спецификация 2025-11-25 задает
