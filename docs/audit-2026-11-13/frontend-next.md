## server-client

**Server и Client Components** · `frontend.server-client` · **8/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/frontend/next/rules/server-client.md) · [Текущий файл](../../registry/standards/frontend/next/rules/server-client.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Привязано к App Router и объясняет минимальную интерактивную границу.

### Что уточнить

1. Нужно назвать версию Next.js и отдельно описать импортную границу use client
2. Серверное исполнение не обеспечивает объектную авторизацию; проверка должна быть у чтения/изменения
3. Нет сценария безопасных props и публичности Server Action как отдельной границы

### Сценарии приемки

1. Сборка не содержит секретов, а props содержат только разрешенный DTO
2. Подмена ID у серверного действия не дает доступа к чужой записи
3. Небольшая интерактивная часть работает без переноса всей страницы в клиентский bundle

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Прочитан полный текст правила и указанные в нем ссылки. Внешние страницы для этого правила отдельно не перепроверялись; релевантность и актуальность требуют проверки при редактуре.

## data-boundary

**Серверные данные** · `frontend.data-boundary` · **5/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/frontend/next/rules/data-boundary.md) · [Текущий файл](../../registry/standards/frontend/next/rules/data-boundary.md)

Применимость 1/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 1/2.

### Что сохранить

Выделяет общую политику контрактов, ошибок и кеша вместо разношерстных компонентов.

### Что уточнить

1. В одном правиле смешаны браузерный API-клиент, серверный DAL и BFF без границ ответственности
2. Не описаны авторизация на сервере, runtime-валидация и допустимый payload клиенту
3. Нет конкретного примера отмены/гонки запросов и приватного кеша

### Сценарии приемки

1. Несовместимый ответ API отклоняется на границе, а не ломает произвольный компонент
2. Приватный серверный payload не попадает в общий кеш или клиентские props целиком
3. Более старый ответ не заменяет результат последнего пользовательского запроса

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

## states

**Состояния интерфейса** · `frontend.states` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/frontend/next/rules/states.md) · [Текущий файл](../../registry/standards/frontend/next/rules/states.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Различает пустой ответ и ошибку, учитывает откат optimistic update.

### Что уточнить

1. Нет полной таблицы loading/refreshing/empty/forbidden/offline/error и допустимых действий
2. Источник WCAG про status messages не заменяет конкретные требования доступности уведомлений
3. Не определено сохранение предыдущих данных и локального ввода при повторе

### Сценарии приемки

1. Пустая успешная выдача показывает пустое состояние, 500 показывает ошибку
2. Ошибка optimistic save возвращает согласованное состояние и сохраняет редактируемый ввод
3. Загрузка и результат озвучиваются assistive technology без неожиданной смены фокуса

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

## performance

**Web performance** · `frontend.performance` · **6/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/frontend/next/rules/performance.md) · [Текущий файл](../../registry/standards/frontend/next/rules/performance.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 1/2.

### Что сохранить

Измерения и реальные устройства важнее механического memo.

### Что уточнить

1. Не названы измеряемые метрики, метод сбора и различие лабораторных/полевых данных
2. Нет воспроизводимых условий сравнения: устройство, сеть, кеш, версия и сценарий
3. Не определены бюджеты и допустимая регрессия для конкретного продукта

### Сценарии приемки

1. До и после сравниваются одна страница, набор данных и профиль устройства
2. Улучшение лабораторного балла при ухудшении пользовательской метрики фиксируется как спорный результат
3. Длинный список, изображения и взаимодействие укладываются в заранее выбранные бюджеты

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.
