## secure-storage

**Keychain и Keystore** · `mobile.secure-storage` · **9/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/mobile/react-native/rules/secure-storage.md) · [Текущий файл](../../registry/standards/mobile/react-native/rules/secure-storage.md)

Применимость 2/2; Точность 2/2; Границы 2/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Точно отличает Keychain от Keystore и не обещает, что биометрия заменяет серверный контроль.

### Что уточнить

1. Не заданы параметры доступности ключа, backup/restore и поведение после переустановки
2. Нет реакции на недоступность хранилища или изменение биометрии
3. Очистка и отзыв при logout должны описывать потерю сети и последовательность безопасного завершения

### Сценарии приемки

1. Токен отсутствует в AsyncStorage, backup открытым текстом и диагностических логах
2. Недоступное защищенное хранилище не вызывает fallback на открытый файл
3. Logout очищает локальные данные, а серверная сессия отзывается согласно явной политике офлайн-выхода

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Открыт React Native Security; описание AsyncStorage и Keychain соответствует источнику. Android Keystore указан как хранилище ключей; параметры реализации выбранной библиотеки отдельно не проверялись.

## deep-links

**Deep links** · `mobile.deep-links` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/mobile/react-native/rules/deep-links.md) · [Текущий файл](../../registry/standards/mobile/react-native/rules/deep-links.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Не доверяет host/path/state и рекомендует подтвержденные платформенные ссылки.

### Что уточнить

1. Не отделена обычная навигация от OAuth callback: не всякая ссылка требует начатую операцию/state
2. Нет описания холодного старта, background-состояния и повторного получения ссылки
3. Не указаны платформа, подтверждение домена и строгий разбор параметров/кодирования

### Сценарии приемки

1. Разрешенная навигационная ссылка открывается и на холодном старте, и в работающем приложении
2. OAuth callback без совпадающей активной транзакции отклоняется
3. Чужой host, дублирующий параметр и старая авторизационная ссылка не создают сессию

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Открыт React Native Security: подтвержден риск перехвата custom URI schemes и рекомендация защищать чувствительные данные. Для конкретных Universal/App Links нужны прямые документы Apple/Android.

## offline

**Офлайн-синхронизация** · `mobile.offline` · **7/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/mobile/react-native/rules/offline.md) · [Текущий файл](../../registry/standards/mobile/react-native/rules/offline.md)

Применимость 2/2; Точность 1/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Сохраняет ключи операций и версии, различает offline read/write.

### Что уточнить

1. Не заданы устойчивое хранение очереди, порядок и зависимости операций
2. Нет сценариев logout/смены аккаунта и истечения серверных прав
3. Не определены конфликтная политика, удаление и срок хранения персональных данных

### Сценарии приемки

1. Перезапуск приложения не теряет очередь и постоянные ключи
2. Два устройства меняют одну revision: конфликт виден и данные не затираются молча
3. После смены аккаунта очередь предыдущего пользователя не отправляется с чужими полномочиями

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки

Прочитан полный текст правила и указанные в нем ссылки. Внешние страницы для этого правила отдельно не перепроверялись; релевантность и актуальность требуют проверки при редактуре.

## native-release

**Мобильный релиз** · `mobile.native-release` · **8/10** · **P1**

[Исходная редакция](https://github.com/sergey-from-riders/vibecoding-base/blob/613500afd8eca5143b4094f6f5cd48e67844f8ff/registry/standards/mobile/react-native/rules/native-release.md) · [Текущий файл](../../registry/standards/mobile/react-native/rules/native-release.md)

Применимость 2/2; Точность 2/2; Границы 1/2; Проверяемость 1/2; Примеры 2/2.

### Что сохранить

Различает обновление JS и нативную совместимость, учитывает политики магазинов.

### Что уточнить

1. Не заданы runtime fingerprint/матрица совместимости для данного механизма обновлений
2. Нет поэтапного rollout и критерия остановки по crash/login-показателям
3. Rollback клиентского bundle не гарантирует обратимость локальных миграций и server API

### Сценарии приемки

1. Bundle с новым native module не доставляется старому runtime
2. Поэтапный выпуск останавливается при согласованной регрессии
3. Возврат к предыдущему совместимому bundle сохраняет локальные данные и работу поддерживаемого API

Сценарии предложены для будущей проверки; фактический результат в конкретном проекте не установлен.

### Источники и границы проверки
