# Промпт для уточнения одного стандарта

Применяйте к одному правилу за проход. Индивидуальное задание находится в [аудите всех 142 правил](../docs/audit-2026-11-13/index.md). Промпт задает редакционную работу; сведения о фактически запущенных проверках необходимо получить отдельно.

Подставьте `RULE_PATH`, `BASE_REVISION`, дату и, если известен, профиль проекта. Если профиль не задан, сохраните узкую область исходного правила и явно отметьте решения, которые должен принять конкретный проект.

```text
Ты редактор инженерных требований и практикующий специалист по теме правила.

Входные данные:
- Репозиторий: sergey-from-riders/vibecoding-base.
- RULE_PATH: <путь к одному rules/*.md>.
- BASE_REVISION: <полный SHA исходной версии>.
- PROJECT_PROFILE: <стек, тип продукта, данные, нагрузка, ограничения или «не задан»>.
- REVIEW_DATE: <фактическая дата содержательной проверки>.
- Индивидуальное задание: <замечания, сценарии и промпт из аудита этого ID>.

Цель: сделать правило достаточно точным для независимой реализации и приемки
человеком и AI-агентом. Сохрани правильное ядро и краткость. Не расширяй тему
до полного учебника и не объявляй собственные предпочтения отраслевой нормой.

1. Прочитай исходный файл целиком, related-правила, описание пакета,
   docs/content-contract.md и docs/contributing-standards.md. Проверяй исходный
   SHA; если файл уже изменен, сначала установи отличие от аудируемой версии.
   Не предъявляй как отсутствие то, что уже описано в связанном правиле.

2. Для каждого существенного утверждения установи его тип:
   - требование внешней спецификации с точной версией и разделом;
   - обоснованный инженерный принцип в заданной области;
   - выбранное соглашение проекта;
   - рекомендация с исключениями;
   - иллюстративный пример, не готовая реализация.
   Проверяй первоисточники. Записывай, что именно подтверждает ссылка.
   Открывающаяся ссылка сама по себе не доказывает корректность утверждения.
   При недоступном источнике обозначь неопределенность и не выдумывай вывод.

3. Определи применимость: тип системы, версии, предварительные условия,
   границы ответственности и случаи «не применимо». Раздели обязательный
   наблюдаемый результат и один из допустимых способов его достижения.
   Не требуй выбранную CMS, Redis, определенную папку, паттерн или числовой
   порог без основания. Если параметр выбирает проект, назови параметр,
   способ выбора и последствия; пример значения подпиши как пример.

4. Сформулируй небольшой набор атомарных требований. Для каждого должны
   быть понятны условие, действие/ограничение и наблюдаемый результат.
   При необходимости используй локальные метки <ID>:R1, <ID>:R2.
   Не вставляй в правило общие инструкции вроде «проверь все».
   Разногласия по стилю или UX не делай универсальным запретом.

5. Разбери только существенные для этой темы границы: неверный ввод,
   отсутствие прав, повтор, конкуренцию, частичный отказ, восстановление,
   совместимость. Соседние механизмы свяжи через related, не копируй целиком.
   Для исключения укажи условие и компенсирующую меру. Отсутствие доступа
   к проверке не превращай в «соответствует».

6. Выбери осмысленные сценарии приемки по риску и применимости: нормальный,
   отрицательный и граничный, когда они относятся к теме. Не вводи квоту. Формат: исходное состояние → действие → ожидаемый результат
   → наблюдаемое свидетельство. Для рискованной темы добавь конкретный сбой
   и восстановление. Данные вымышленные. Не выдавай описанные сценарии за выполненные тесты.
   Отдельно укажи, что реально проверено документально или запуском,
   что только предлагается проверить и что заблокировано.

7. Сохрани одну сравнимую пару «Плохо / Хорошо». Если это псевдокод,
   обозначь ограничение. Проверь, что хороший пример не нарушает собственную
   норму. В блоках «Человек» и «Агент» оставь конкретное решение/действие
   этой темы; общие обязанности не повторяй. Ранее выданные полномочия
   и правила действующего проекта учитывай явно, без лишнего согласования.

8. Сохрани совместимость публикации: существующие ID, путь, section,
   published_at и schema_version: 1. JSON-совместимый frontmatter остается.
   sources полностью совпадает с разделом «Источники», related ведет
   к существующим ID. H1 совпадает с title. Разрешенные H2:
   Коротко, Плохо, Хорошо, Почему, Когда применять, Как проверить,
   Человек, Агент, Пример применения, Источники.
   Новые смысловые блоки размещай как H3 внутри подходящего H2.
   В «Плохо» и «Хорошо» по одному fenced block. Новые метаданные и H2
   требуют отдельной версии контракта и согласованного изменения импортера.
   reviewed_at обновляй только после фактической содержательной проверки.

9. Выдай:
   а) краткую оценку исходника: применимость, точность, границы,
      проверяемость, примеры — каждый критерий 0–2;
   б) список «сохранить / уточнить / исправить / вынести в соседнее правило»;
   в) полный исправленный Markdown;
   г) таблицу сценариев и статусов фактической проверки;
   д) источники и подтвержденные ими утверждения;
   е) несовместимые изменения, решения проекта и нерешенные вопросы.
   Дополнительные стандарты предложи отдельно; не выдавай их за уже принятые.

Не удаляй существующие генераторы, проверки, профили и примеры проектов.
Для изменения правила пересобери производные standard.md и примеры штатными
командами из docs/contributing-standards.md. Изменения инструментов делай
только при подтвержденном дефекте и проверяй отдельными тестами.
Успешное чтение правила не доказывает соответствие проекта этому правилу.
Пиши по-русски и технически точно.
```

## Как принимать результат

Независимый читатель должен определить, когда правило действует и какое наблюдение опровергнет соответствие. Если два разумных исполнителя могут выбрать разное поведение и оба сослаться на тот же текст, уточните контракт или явно разрешите оба варианта. Большее число слов не является критерием улучшения.
